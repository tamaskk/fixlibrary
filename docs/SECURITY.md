# Security: FixLibrary

Read before changing IPC, file operations, downloads, updates, external process calls, secrets or deletion. Where this file is stricter than AGENTS.md §05, this file wins.

## 01 What we protect

| Data            | Examples                                           | Sensitivity                           | Where stored                                                                                                | Retention                                                                                                                                                                                                                                                        |
| --------------- | -------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Music library   | MP3, AIFF, WAV files on the external drive         | Irreplaceable to the user             | The library folder; backups in `FixLibrary Backups`                                                         | Originals are never deleted by the app, with one exception: a WAV that was converted to AIFF in place goes once the AIFF is there, and is then in the backup folder until a later batch is applied. Backups of older batches are deleted when a batch is applied |
| Lookup API keys | AcoustID key, Discogs consumer key and secret      | Secret                                | Encrypted with Electron `safeStorage` (macOS Keychain) in the `settings` table; `.env.local` in development | Until the user removes them in Settings                                                                                                                                                                                                                          |
| App database    | Track metadata, analysis cache, batches, playlists | Low                                   | `~/Library/Application Support/FixLibrary/fixlibrary.db`                                                    | Until the user deletes it                                                                                                                                                                                                                                        |

There are no accounts and no personal data of other people.

## 02 Trust boundaries

- Renderer → main: untrusted. Every IPC payload is validated with Zod: its shape in the handler in `src/main/ipc/`, and for the calls that take one request object (`library:run`, `preview:*`) its content in the pipeline function the handler calls, before anything acts on it.
- Python sidecar → main: validate RPC results against the types in `src/shared/rpc.ts`. A crash or malformed line never takes the app down.
- Online services (AcoustID, MusicBrainz, Discogs, iTunes, Cover Art Archive, GitHub API): untrusted input. Validate before use; never render as HTML. A lookup answer is read with a schema, entry by entry; its text is cut to one clean line of 300 characters before it is kept or proposed, an id is taken only as a UUID, and at most 1 MiB of an answer is read. A request goes to a fixed host, follows no redirect, and ends after 6 s. The one exception is the picture of a cover: it is asked without a key, read up to 16 MiB within 15 s from its first request, refused unless it says it is a JPEG or a PNG, and fetched only from the host of its service over `https` on the default port (`isImageUrl`: `is<n>-ssl.mzstatic.com`, `coverartarchive.org`, `archive.org` and its servers, `i.discogs.com`), because its address comes from a service's answer; the redirects of the Cover Art Archive are followed by hand, at most three, each address checked before it is asked. A row can be looked up again from the preview at most once in two seconds, one row at a time, so a page cannot hold the services at their limits with the owner's keys; the "Teszt" requests of Settings are not counted by the lookup limiters. A lookup sends the fingerprint and length of a track to AcoustID, and its artist and title (from the tags, or the file name), and for a remix its mix, to MusicBrainz and Discogs; the search for a cover sends the artist and title to iTunes Search and the MusicBrainz id of the release to the Cover Art Archive; the online recommendations (T-038) send the user's list of styles, the profile of a playlist and the names, style, tempo and key of up to 20 of its tracks to Claude, and the names Claude proposed to YouTube as a search, less those a track of the library has exactly (normalized artist and title), one request at a time and 30 s apart; a gap of the generator (T-039) sends the style, tempo, key and energy it needs instead of tracks; the generator's prompt sends what the user typed and the list of styles to Claude, one prompt at a time; a gap's style goes by its id and its key must be a Camelot key, so no text of the page reaches a prompt; nothing else of the library leaves the machine.
- `claude` CLI output: untrusted. Validate with the JSON schema and the Zod schema; values are data, never commands or paths.
- Files in the library: untrusted. File names and tags may contain any character; tag text and XML are escaped on write. Tag text read by a scan is cut to one line of at most 300 characters in the sidecar, without characters that reverse the reading direction, and the main process refuses anything longer. The main process checks every file's tags again and refuses text that is not one clean line. A scan never follows a link out of the library: the walk skips links and re-checks a folder before entering it, and the sidecar opens a file only if no part of its path is a link (`O_NOFOLLOW_ANY`). The sidecar picks the parser by the file's extension and never reads more than 16 MB at once. Audio is decoded only by the app's own ffmpeg, which has no network protocol: the sidecar opens the file under the same rules and hands it over as standard input, with the input format forced by the extension, `-protocol_whitelist pipe`, an empty environment and a timeout, so a file can name nothing for ffmpeg to open. ffmpeg may ask for at most 128 MiB at once (`-max_alloc`), which refuses a header that claims an absurd sample rate before the resampler takes gigabytes. The FFmpeg inside the Essentia wheel never decodes a library file. At most the first 10 minutes of a file are decoded for tempo and key, 20 minutes (and one second, to tell a longer file) for the stems, kept as 16 bit (212 MB at most) with one minute at a time made float. What ffmpeg prints is logged as one line without control characters. The workers that analyse end with the sidecar. Not bounded: the time and memory Essentia takes inside a worker, and the memory Demucs takes; Demucs runs in a thread of the sidecar process itself (one job at a time), so a file that makes it take too much takes the sidecar down, which the app restarts. A Demucs job told to stop answers at once; its worker ends after the minute of audio it is in (seconds on MPS, longer on the CPU) and writes nothing. The bridge waits 30 seconds longer than the stage, so a job that runs out of time is always told to stop. File system errors are logged as one line written by the app, never as the raw error, because a file name can hold a line break.
- Downloaded executables and archives (yt-dlp, Python runtime, app updates): untrusted until their SHA-256 matches the published value.
- The release workflow (T-044) holds no secret: it uses only its own token, with `contents: write` for its one job, and makes a draft. The release key never reaches GitHub; the owner signs a release on their own machine after checking the draft holds the files its manifest names. The tag reaches the shell only through an environment variable. The actions are pinned to commits.
- The updates (T-043): the app asks `api.github.com` for the latest release of `tamaskk/fixlibrary` and of `yt-dlp/yt-dlp`, without a token, and downloads only from GitHub's hosts (`github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`), following at most three redirects by hand, each address checked, over `https`. An app update is trusted only through `manifest.json` whose Ed25519 signature (`manifest.json.sig`) matches the public key built into the app (`services/release-key.ts`) and whose version equals the release's tag and is newer than the app's, so an older signed release cannot be served as a new one; the private key stays with the owner, outside the repository (`npm run release:key`, which refuses to replace a key the app has without `--force`), and a build without a key never updates the app (yt-dlp still updates, see below). An answer that is not a download is read up to 1 MiB, counted after decompression; the headers must come within 30 s, and a download that gets no byte for a minute, or takes an hour, is stopped. Every file is downloaded to a `.part` next to its place (created anew, never written through a file or link already there), hashed on the way, refused beyond the size the manifest names, and renamed into place only when its size and SHA-256 match; anything of a release that failed is deleted. A new runtime is unpacked ahead by the same path as the bundled one (`installRuntime`), so its `.ready` mark holds the hash the signed manifest named. The DMG is opened by `shell.openPath` only by the user's click, from a path main chose, after its SHA-256 was checked once more. The user may ask for a check once a minute, which keeps the API's limit of 60 questions an hour for the scheduled ones. yt-dlp is downloaded as the platform-independent zipapp, kept in `userData/bin` as a file of its own per version (a yt-dlp that runs is never changed under it), run once with `--version` before it is made current, and run by the runtime's interpreter with `-I` only while it is newer than the runtime's own. Accepted for now, by the owner's choice: its `SHA2-256SUMS` comes from the same release, so it proves the file is whole, not who published it; whoever can publish a yt-dlp release can run code in the app within a week (six hours after an extraction failure). The fast fix of a broken site is worth it here; checking yt-dlp's GPG signature would need an OpenPGP verifier, a new dependency. A process of the same user that can write `userData/bin` can do the same, as with the unpacked runtime. Also accepted: whoever controls the GitHub repository without the key can keep users on an older release by marking it the latest (the manifest has no expiry).
- The Python runtime (T-041): its packages are installed from the lock with their hashes and as wheels only (`--no-build`), so neither a wheel that is not the locked one nor the build tools of an sdist get in; fixlib_py is built offline by uv's own backend. The archive inside the app is checked for its size, then hashed in the same read that feeds the system's `tar` (an argument array, an empty environment), so what is unpacked is what was hashed; it is unpacked into a folder of the app's own and marked ready and renamed into place only when its SHA-256 matches the manifest. bsdtar strips a leading `/` and refuses `..` and writing through a link. The sidecar starts with `-s -P`: neither the user's own site-packages nor the working folder come before the runtime's packages, as a standalone Python would read both. Accepted for now: on later starts the unpacked copy in `userData/python/<version>` is trusted by its `.ready` mark (the archive's SHA-256) and the presence of its interpreter, not file by file, so a process of the same user could change it; the app is signed ad hoc without the hardened runtime (see Packaging and signing), so such a process can also inject a library into it. Before the app is signed for real, the runtime is to be kept in the sealed bundle or checked against a list of file hashes at start.

Packaging and signing (T-042):

- The app is signed ad hoc (`identity: '-'`), without an Apple Developer ID, without the hardened runtime and without notarization, by the owner's choice: with the hardened runtime, library validation refused the frameworks of an ad hoc signature. So a process of the same user can inject a library into it, and a debugger can attach where the developer tools are enabled. There are no entitlements.
- Electron fuses (`electronFuses`, checked by `scripts/build-dmg.sh` after every build): `RunAsNode`, `EnableNodeOptionsEnvironmentVariable` and `EnableNodeCliInspectArguments` off, so no one runs code as the app through `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` or `--inspect`; `EnableEmbeddedAsarIntegrityValidation` and `OnlyLoadAppFromAsar` on, so the app loads only the app.asar whose hash its signed Info.plist names; cookie encryption on. `GrantFileProtocolExtraPrivileges` stays on: the page is loaded from a file.
- The README tells the user to allow the app once in System Settings → Privacy & Security, to download it only from the GitHub releases of the repository and to compare its SHA-256 with the one the release names, and never to turn Gatekeeper off or strip the quarantine attribute.
- The lite DMG carries only the runtime's manifest; it trusts a runtime that is unpacked already by its `.ready` mark, as the full app does on a later start.
- An update the app downloads itself (T-043) carries no quarantine and so passes Gatekeeper; with an ad hoc signature there is no signer to check. The updater is then the root of trust: it verifies the Ed25519 signature of the release manifest before it trusts a DMG or a runtime (see the updates above).
- Open: the Electron the app ships (39) is out of the supported releases, and `npm audit` names advisories that a newer major fixes; an upgrade is to be its own task before a release is published (T-044).

## 03 Authentication and authorization

- There is no login and no session. The only principal is the local macOS user.
- The renderer has no privileges of its own: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, and a CSP of `default-src 'self'`, which lets media come from `fixlib-audio:` as well (`media-src`, T-030).
- The preload exposes named functions only. It never exposes `ipcRenderer`, a generic `invoke(channel, …)`, or a function that takes a file path to execute or a command to run.
- An event from the main process reaches the page through a subscribe function of the preload that passes on the payload only; the page never gets the event object or a way to listen on a channel of its choice.
- Navigation and new windows are denied; only `http(s)` links are handed to the OS browser. The window stays on the app's own page (`will-navigate`, `will-redirect` and webviews are blocked), so a dropped file or a changed `location` cannot load another document into the window that holds `window.api`.
- Every IPC handler checks that the call comes from the main frame of the app's own page, and validates its arguments, before it runs.
- A run is started with track ids and function names only. Which tracks run is decided in the main process, twice (when the request arrives and when the batch is built); a function name is accepted only if it is one the user can ask for, so a page cannot name an apply stage. The stage that writes what a chosen function proposes joins the batch by itself, and its jobs run only after `preview:approve`. Starting a run and pausing or resuming one are rate limited in the main process. Pause, resume and cancel take no argument: a page can only act on the one active run. One run is active at a time, enforced in the main process.
- Custom protocols (such as the planned `fixlib-audio`) serve only files that belong to a track in the database, resolved by track id, never by a path from the renderer.

## 04 Secrets

- Stored in: `.env.local` during development (gitignored), and encrypted via `safeStorage` in the packaged app. Never in git, never in the renderer, never in logs, never in plain text in the database, never in the `.dmg`.
- The packaged app ignores `.env` files.
- CI and the release workflow need no API keys. Do not add one.
- Rotation: the user regenerates the key at AcoustID or Discogs and re-enters it in Settings.
- What the encryption covers: the database file at rest. A copy or backup of the file, another macOS user, or a process that can only read files does not get the keys. What it does not cover: code running as the same user. The app is ad-hoc signed, without the hardened runtime and not notarized, so such code can inject a library into the app's binary (`DYLD_INSERT_LIBRARIES`) and ask the Keychain as the app; the fuses close the easier ways (see Packaging and signing). The encryption gives confidentiality only: it does not detect a changed ciphertext, which is why each key is encrypted together with its name.
- The Settings page can save, replace, delete and test a key, but never read one back. The "Teszt" request sends the key in the request body (AcoustID) or the `Authorization` header (Discogs), never in a URL, to a fixed host, without following redirects. No second request goes to a service within five seconds, and saving or deleting a key does not reset that.
- `.env.local` is read into memory in development only and is never copied into `process.env`.

## 05 Input, output, injection

- The `claude` command is found by a login shell that runs a fixed line; what it prints is only ever checked as a path (absolute, named `claude`, an executable file). A command the user picks in the main process's file dialog is accepted when it is an executable file that answers `--version` as Claude Code does; its path is stored under the settings key `claude`, which only that dialog writes, and is checked to be an executable file again before every call. The renderer never names a program. A call is started with no built-in tools (`--tools ""`), no MCP servers (`--strict-mcp-config`), no user, project or local settings and so none of their hooks or permissions (`--setting-sources ""`), no skills (`--disable-slash-commands`) and the app's own system prompt, in an empty folder of the app with a minimal environment in which the system's folders come first on the `PATH`. Settings managed by an organisation still apply; the app does not turn those off. An answer is taken only from a call whose stream said at its start that it has no MCP server and no tool but the one the answer is given through; a call that says otherwise is stopped at once, and a stream that never says it is not trusted. An `@` in the data of a prompt is written as an escape, so the tool takes no tag for a file to attach. What goes into a prompt (tags, lookup results) is data: it is sent as JSON after being cut to one line, the system prompt says so, the answer must fit a JSON Schema and then a Zod schema, and an answer can only ever be a value of a field, never a command or a path. `claude auth status` prints the account's email and organisation; the app uses only whether someone is logged in and the kind of subscription, and logs neither its output nor the output of a call. The app does not hand `claude` an API key, but it cannot make the login a subscription: when the login reports no subscription, Settings says that calls may be charged. The artist, title, mix, remixer (read from the mix), label, year and tempo of the tracks that are asked about, the genre of their tags and the genres and styles Discogs files their release under, and the names of the user's styles, go to Anthropic under the user's own Claude account; nothing else of the library does. Twenty tracks share a call, so the text of one track could try to steer the answers for all of them, also the choice among the styles the list has: what Claude answers is a proposal the app's rules decide on, and the preview, where every style shows and can be changed, is the control. A track whose text reads like it talks to the model (words such as "ignore", "classify", "confidence", "every track", or a genre of more than four words or 40 characters) is asked about in a call of its own. A name in an answer is taken as data of at most 40 characters; a name the rules cannot take makes the track Unsorted. A style Claude names that the list does not have is taken only when one of that track's own genres (its tag, or what Discogs files its release under) names it, when it is no house style, and when it is a plain genre name (`newStyleNameSchema`: ASCII letters and digits, spaces, `&'+-`, at most 30 characters and four words, none of the app's own folder names); otherwise the track is Unsorted. The text of a tag can still name such a style for its own track: the approval names the new styles, a batch creates five at most (the first its rows name; the tracks of the others stay Unsorted), and none once the list holds 50. A name within one letter of "house" counts as a house style. A style the user types may not hold `/ \ : * ? < > | "`, start or end with a dot, or be named like a folder of the app's own (`_Duplicates`, `FixLibrary Backups`, `Inbox`), because styles become folders.
- External tools (`yt-dlp`, `ffmpeg`, `fpcalc`, `mp3gain`, `claude`, `python`) are started with `spawn(binary, argsArray)`. No `shell: true`, no `exec` with an interpolated string. A user-controlled value that could start with `-` is preceded by `--` or passed as an option value.
- Paths: every write target is resolved and checked to be inside the library root, the clean library folder, the backup folder, the Inbox, or Electron `userData`. Reject `..` segments and absolute paths from the renderer.
- File names built from metadata (`pipeline/naming.ts`) replace what a file system refuses or reads as something else (`/`, `:`, `\`, `|`, `*`, `<`, `>`, `"`, `?`, control and invisible characters, a leading dot), are composed (NFC) and are limited to 220 UTF-16 units and 228 UTF-8 bytes. A name is only ever a name: the rename stage joins it to the folder the file is in, checks it again and writes only a name as the naming builds one (`isBuiltFileName`: the rule of the preview, and none of the characters above, no leading space, the byte limit), and refuses a name whose extension differs from the file's, so a rename cannot move a file or change what kind of file it is. It never writes over a file: a name that is taken gets ` (2)`, also when the file that has it spells it in another Unicode form. The rule for names is applied to the new parts of a path only (the file name, and folders that do not exist yet); a folder the file is in already keeps its name, a move into another existing folder is refused when that folder is hidden or its name holds an invisible character, and whether the target is inside the library is decided by what the folders are on disk.
- The apply phase starts only through `preview:approve`, which takes a batch id and nothing else: which rows are written is what the main process stored for that batch, and the batch must be the one that waits for approval. `preview:edit` accepts six fields by name, each value checked by the schema proposals are read with (one line of at most 300 characters, an energy of 1 to 10, a style that exists); a file name can never be set from the page. Tracks are named by id. Text of a field may hold no control character, line break or invisible formatting character (`UNSAFE_TEXT` in `shared/file-names.ts`: direction marks, zero-width characters including the joiners, the soft hyphen, tag characters), and a proposed file name must be one the rename itself accepts (`unusableNameReason`: no `/` or `:`, no leading dot, an audio extension, composed Unicode), so the preview shows no name the file system rule refuses (the rename itself is stricter still, see above, and writes only a name as the naming builds one); a proposal is read field by field, and a field that is not valid is neither shown nor handed to the stage that writes. A successful approval happens once per batch and a successful undo once per batch that wrote, and each is refused while the other or a run is on its way, so neither has a rate limit of its own; a call that is refused changes no file. What a stage stores in `batch_items.after` beside `fields` and `warnings` reaches its apply stage as stored: a stage must validate its own keys with a schema before it uses them. The confirmation of an approval or an undo is a dialog of the page, not of the main process: a page that is not the app's own cannot call these channels at all, and the packaged app loads no remote content.
- Library files change only in the apply phase, through `src/main/services/file-ops.ts`: backup or copy first, write to a temp file in the same folder, rename on success. That module checks every path it writes, renames or deletes, and every source it copies, against the library, clean library and backup folders as they are on disk; it refuses paths that are not plain and sources that are links, and it never gives a file a name that is taken. It is the only place where a file is deleted, and it deletes what its caller names; which files those may be is decided in `pipeline/batch-files.ts`: temp files of interrupted writes (by their name pattern, at startup), the file a batch left under a new name (on undo, only the track's current file and only if the journal names it), backups of batches older than the last one that wrote and backups an undo has put back (only files inside the backup folder), folders those deletions left empty (never one of the three folders), the old folders a move into a style folder left with nothing in them but Finder's `.DS_Store` (that file with them; never the root, a style folder or a folder of the app's own, and nothing else in a folder: `FileOps.removeFolderOfFinderData` reads the folder and refuses any other entry, a `.DS_Store` that is not a plain file, a folder that is a link, a folder that is no longer the one it read, and a folder that is one of the three; best effort, so a failure never fails the move or the undo; undo removes such a style folder too once it has put the files back, and a folder of the app's own only when it is empty), and its own temp file after a write that failed. The rows undo acts on are checked by role before anything changes: a backup must lie in the backup folder, a restore target in the library or the clean library. Undo never writes over a file that is not the track's own.
- `preview:keepDuplicate` takes a batch id and a track id and nothing else, for the batch that waits for approval and a track that is in one of its groups; it changes which copy is marked to keep, never a file. Where a copy goes is not the renderer's to say: the folder name `_Duplicates` is a constant of the main process, `TrackFiles.setAside` accepts a folder name and never a path, and the target is checked like every move (inside the library, never over an existing file). A `_Duplicates` that is a link is refused, and nothing is moved unless the copy that stays is a file on disk at that moment. The confirmation of an approval names how many files go to `_Duplicates`, whether or not the tab was opened: metadata from tags and lookups decides the groups, so the user is told before files leave the library. The scan points a track that was set aside back at a file only when that file has the size and the modification time the track had, and undo does not take the scan's word for it: before the backup is written over a file that is not plainly the track's own, the two are compared byte for byte, and a file of another track, under any spelling of its name, is never written over. An approval is refused (`PREVIEW_CHANGED`) when the groups the batch holds are not the ones that follow from its rows, so a failed regroup cannot let through what was never shown; a keeper chosen just before the approval is part of what is approved. Setting aside deletes nothing. Undo removes a file under a name the batch gave only when it is provably the batch's own: it holds what the batch wrote down as written (`batch_files.sha256`), or, for a file that was only moved or copied, what its backup or its original holds. A file the user put there since stays, and is counted for the user to see.
- `convert.wav_to_aiff` writes one file, the temp file the file rules of the main process named: an absolute path next to the source, with the shape of the app's temp names. The sidecar makes that file itself (`O_CREAT | O_EXCL`, no link followed) and afterwards touches the path only while it is still that file. The source is untrusted: it must say of itself that it is a WAV of plain samples before libsndfile parses it, it reaches ffmpeg as standard input with the demuxer and the decoder fixed and only the `pipe` protocol allowed for reading, and the output is limited to the size the header promises. Tags are copied as data. Whether a frame is compressed or encrypted is asked inside the one reader that would unpack it, not by a second parser; such a frame, or a tag over 16 MiB, fails the track. After a conversion the old WAV is removed from the library. This is the one deletion outside undo, and it happens only while every byte of the file is in another file: its backup in the backup folder, or the original of a clean library copy, compared byte for byte before the conversion, again before the new file is put in place, and once more at the moment of removal; the removal of a leftover by a later attempt is under the same condition (see ARCHITECTURE, WAV to AIFF).
- `tags.write` changes no file where it is: it writes a copy with the new tags into the temp file the main process named, made new by the sidecar and known again by its identity, and reads it back before it answers. The fields are checked on both sides (one clean line of at most 300 characters, a year, a tempo and a key in range, a cover that is named by its name in the app's covers folder and read there as a 600 × 600 JPEG of at most 4 MiB, decoded by Pillow, not judged by its first bytes). The tag the file already has is read, every time and by the one reader there is, through frame classes that refuse packed frames; a tag of more than 5000 frames is refused before it is read (a limit on the work a hostile tag can cost), as is an MP3 whose tag counts audio as its own; the audio of the result is compared byte for byte with the audio of the source. The main process puts the result only in the place of the content the sidecar read (hashed before and at the rename), and undo writes a backup over a file only while the file holds what the batch wrote or what the backup holds, whatever the journal says. A backup is deleted outside undo and pruning in one case only: the first change of a track failed and the file is byte for byte what the backup holds.
- `analysis.loudness` reads a file whole, as ffmpeg's standard input with the demuxer fixed by its name, and takes only the last summary of the `ebur128` filter from what ffmpeg prints, by anchored patterns; tag text ffmpeg prints comes before it and cannot pass for a value. `normalize.apply` writes one file, the temp file the main process named, made new by the sidecar and known again by its identity, in one of three ways the main process chose, checked on both sides (a whole number of steps other than 0 and at most 26, or a gain other than 0 and at most 40 dB): mp3gain on a copy (`-T -g <n> -s s -q`, an empty standard input, no environment; the size of the result must be the size of the source), the samples of an AIFF or WAV multiplied in the copy only between the bounds of its sample chunk (header fields read from at most 64 bytes, samples the header promises that the file does not hold refuse it), or ffmpeg encoding the MP3 again into at most twelve times its size with the source's ID3v2 tag written back, the tag read as for `tags.write` (at most 16 MiB and 5000 frames, no packed frames). The main process puts the result only in the place of the content it hashed, which is the content the sidecar was given to read.
- Accepted risk, by the owner's choice (2026-10-17): mp3gain 1.6.2 is old C code with published memory-safety flaws, and it parses the frames of the MP3 it changes. It runs as the user, with the access the user has; only a file the user approved for lossless normalization reaches it. mp3gain and ffmpeg also open the temp file they write by its name, so someone who can write into the library folder could swap it for a link between its creation and their opening it. Both are for a sandbox of the writing tools (`sandbox-exec`, T-046), which also covers `convert.wav_to_aiff`.
- The `fixlib-audio:` protocol (T-030) gives the page audio and nothing else: `fixlib-audio://track/<id>`, a whole number the main process looks up in the database, never a path; a track that is offline, missing or set aside is not served; the file is opened with no link anywhere in its path (`O_NOFOLLOW_ANY` on macOS) and `O_NONBLOCK`, so a FIFO in its place cannot hold a thread, and must be a regular file of `.mp3`, `.wav`, `.aif` or `.aiff`; only GET and HEAD, one byte range per request, `nosniff`; at most eight responses hold a file open, and one not read for 30 s lets it go. A page asking for many waveforms gets one made at a time, for the track it asked for last. The scheme is registered without `supportFetchAPI`, and the CSP lets it be used by media elements only. It is `corsEnabled` for the A/B player of T-033, which reads the samples through Web Audio: a response carries `Access-Control-Allow-Origin` only when the request names the app's own page as its origin (the dev server's, or `null` for the packaged page, which is a file) and its address holds the read token of this launch (`?read=`, 128 random bits made by the main process, given to the main frame of the app's page only through `app:audioReadToken`, compared in constant time); `Vary: Origin` always, never `*`. The origin alone would not do: every opaque document is `null`. `corsEnabled` lets XMLHttpRequest reach the scheme, which the CSP's `connect-src 'self'` refuses; fetch is refused by the scheme itself. The CSP also refuses frames, workers, objects, `<base>` and forms (`frame-src`, `child-src`, `worker-src`, `object-src 'none'`, `base-uri 'none'`, `form-action 'none'`), and the main process blocks the navigation of any frame that is not the main one (`will-frame-navigate`). A custom scheme for the page itself, which would give it an origin of its own, is T-048. An AIFF's header is read for at most 1000 chunks and 64 bytes of its COMM chunk, and served only when the samples it promises are in the file. `analysis.peaks` writes `<track id>.json` into the peaks folder (made by the main process, mode 0700, a link refused) through a descriptor of the folder, a new temp file and a rename; the main process reads it back only through a descriptor opened without following a link, as a plain file of at most the size twenty minutes of peaks take, checked by a schema, after the folder was checked.
- Pictures for covers are untrusted, from a tag or from a service. They live in one folder of the app (`userData/covers`, mode 0700, refused when it is a link), which the main process names to the sidecar when it starts it (`FIXLIB_COVERS_DIR`); every call names a file of it by a name of the app's own shape (a SHA-1 and a fixed ending), never by a path, and the sidecar opens it without following a link. `cover.prepare` and `cover.inspect` decode a picture only as JPEG or PNG, only after its header said it has at most 16 million pixels (a JPEG decoded at the smallest scale that still serves), and say what failed in fixed words. A picture the user chose is read by the main process from the path a dialog of its own gave, or from the path the preload learned of a file dropped on the page (`webUtils.getPathForFile`, which knows only files the user dropped or chose; the page never names a path): it must end in `.jpg`, `.jpeg`, `.png` or `.webp`, lie outside `/net/` and `/Network/` as the path resolves, in any case (opening a file there can mount a share; a share the user mounted under `/Volumes` is accepted), be read within 20 s, be a regular file reached without a link at its end, and is read into a buffer of 16 MiB and refused when that fills, whatever size the file claims; the preload sends nothing for a file without a path, and the dialog opens only for a row that could take a picture; it is copied into the covers folder and only that copy is decoded, where WebP is allowed for such a picture and for the thumbnail of a download (T-034), which comes from the uploader and is decoded by the cover stage without a user's action: Pillow, with its libwebp, is pinned by `uv.lock`, and its advisories are security updates. A placeholder may be drawn again in the apply phase, from the artist, title and style the user approved in the same preview, into the covers folder only; that picture was not shown before it is written. Text drawn on a placeholder is tag text, checked as one clean line on both sides, and only ever drawn, no more than 160 letters of it, each measured once, so no text can keep the sidecar drawing for long. The cover written is made anew from the pixels: nothing of the picture's metadata (EXIF, colour profile, comments) reaches the file. The page gets thumbnails only as `data:image/jpeg` addresses that main read from that folder (at most 256 KB, starting as a JPEG), by batch and track id, and shows them only when they look so; the CSP allows `data:` images and no other source.
- SQL goes through Drizzle with bound parameters. No string-built SQL.
- The Rekordbox export the app reads (T-026) is untrusted: the newest plain `.xml` of the export folder, opened once with `O_NOFOLLOW | O_NONBLOCK`, checked as it is open, at most 64 MB read, refused when it declares a DOCTYPE or entities (no entity can expand), and parsed in a worker thread with a 1 GB heap and a one-minute limit, so a hostile file ends the worker, not the app. Every attribute is validated with a schema before it is used. Its paths are only compared and looked up, never written to; none in a network folder (`/net`, `/Network`) or on a drive that is not connected is looked up. What goes to the page is counts and at most 200 entries per list, each made one line.
- The Rekordbox wizard (T-027) takes from the page only an action of a fixed shape (`wizardActionSchema`); paths are resolved in the main process, and what it copies to the clipboard (`rekordbox:copyPath`) is the app's own XML path or the export folder of Settings, chosen by a fixed name (`xml`, `exportFolder`), never a path the page sends; a step is refused while an XML is read or written, and copies are limited to one a second.
- The Demucs model (T-028) is never fetched by the app. Its weights are downloaded once by `scripts/fetch-demucs-weights.sh`, checked against a pinned SHA-256, unpickled only there, and turned into a tensor file the sidecar loads with `weights_only=True` and a JSON of the model's arguments, so a changed file cannot run code. Demucs's own `get_model()`, which follows a moving branch and falls back to an unchecked download, is not used. The model's arguments are fixed in the code, and the weights file is opened without following a link; what is built is checked (its four stems, 44.1 kHz). The stem envelopes are written only into the app's stems folder (0700), under the track's id, through a new temp file opened in that folder by its descriptor, and renamed there; a temp file a stopped sidecar left, and the envelopes of tracks that are gone, are removed by their exact names, plain files only. The download is capped at 200 MB and 15 minutes, https only, also for redirects, and the new model replaces the old one by a rename.
- XML is produced by a serializer that escapes values, never by string templates. The Rekordbox XML (`services/rekordbox-xml.ts`) is the only file the app writes outside the library, its own data and the covers folder: one fixed name in the folder Settings names, chosen in the main process's dialog, written to a new temp file (`O_EXCL`, so no link is followed) and renamed over the old one. Paths, names and tags in it are untrusted text: escaped by the serializer, with characters XML cannot hold dropped. Nothing is deleted there but the app's own temp files: the one of a failed write (only once this write made it), and those a stop left, by their exact name and only when they are plain files. The folder cannot be in the app's data folder or the backup folder, and one write may start at most every two seconds.
- No `dangerouslySetInnerHTML`. No remote scripts, fonts or styles in the renderer.
- Downloads (T-034): single items only. An address is accepted only from the hosts of YouTube and SoundCloud over https (http is made https), without credentials or a port, and only after yt-dlp said it names one track (an answer of a playlist is refused). It is passed after `--`, so it cannot be read as an option; a search term is the fixed prefix `ytsearch10:` or `scsearch10:` and one line of at most 200 characters. yt-dlp runs with `--ignore-config`, `--no-plugin-dirs` (the config switch leaves plugins of the user's folders on) and `--no-cache-dir`, with only the YouTube and SoundCloud extractors (`--use-extractors youtube.*,soundcloud.*`, so no address reaches the generic extractor, which follows a page to any host), the fragment of an address dropped (it can smuggle data to an extractor), in an environment of a system `PATH` only, so nothing the user or the system configured for it, and no key of the app, reaches it. The Inbox must be a folder, not a link, before yt-dlp writes into it; the folders of the app it writes into are checked like the covers folder (no link, the user's, 0700). Quitting stops every download and question, and nothing that waits in line starts after it. The MP3 goes into `<library root>/Inbox` only; what yt-dlp writes on the way, and the thumbnail, go into folders of the app's own (`userData/download-tmp`, `userData/thumbnails`, mode 0700). Titles and names yt-dlp reports are untrusted text, cut to one line of 300 characters. At most 2 downloads at a time.
- Rate limits: obey each lookup service's published limit and send an identifying User-Agent.

## 06 Dependencies

- New dependency, bundled binary or online service → ask first.
- Bundled binaries are built or fetched at pinned versions by `scripts/fetch-binaries.sh` and checked for the arm64 architecture. Packaging refuses to run if `resources/bin` is missing, incomplete or changed since the script installed it.
- ffmpeg is built without network protocols. yt-dlp is a pinned Python package of the runtime; the updater may download a newer one from yt-dlp's own release (see the updates above).
- Self-updating components (yt-dlp, Python runtime, app) are installed only after a SHA-256 check against the release manifest or checksum file.
- Essentia is AGPL-3.0; the repository stays AGPL-3.0.

## 07 Incident basics

- Contact: the repository owner (tamaskk).
- A leaked secret: rotate first, then clean the history.
- Looking for what happened: `main.log` and `python.log` in the log folder, which the Settings page opens ("Logmappa megnyitása"). They hold stage errors and tool output, never a key. That rests on rules, not on a filter: a key is sent in a request body or header and never in a URL; code that talks to a service catches its own errors and raises one with fixed text; a request, response or config object is never passed to the logger (an object is written out in full, an `Error` only as its stack). As a second line of defence the logger replaces the values of the stored keys in every message, text detail and error before a line is written (`maskSecretsInLog`); a value inside an object passed as a detail is not covered, which is why no object is passed. The mask also covers a key as it would stand in an address, and uncaught errors. Its limits: the values are read from the Keychain at most every five seconds, so a key saved a moment ago is not masked yet, and a key cut in two by the shortening of an error text is not found. The lookup clients raise a `LookupError` whose text is only the service, the kind of failure and the status: what a failed request or its answer said is never passed on. The AcoustID key travels in the body of a POST and the Discogs keys in a header; the kept answers are named by a hash of the fingerprint, never by a key.
- A bad batch on real files: stop, use "Undo last batch", and do not apply another batch (it would delete the backups) until the cause is understood.
