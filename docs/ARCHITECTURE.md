# Architecture: FixLibrary

Sections 01–05 describe the target structure. Only the scaffold exists today: `src/main/index.ts`, `src/main/ipc/app.ts`, `src/preload/`, `src/renderer/` (one page) and `src/shared/ipc.ts`. Everything else is marked by task number in `docs/TASKS.md` and detailed in `docs/source/fixlibrary-fejlesztesi-terv.md`.

## 01 System overview

```
Renderer (React, sandboxed)
    |  window.api  (typed IPC, src/shared/ipc.ts)
    v
Preload (contextBridge only)
    |
    v
Main process (Electron, Node)
    |
    +--->  SQLite (better-sqlite3 + Drizzle)        app state, cache, jobs
    +--->  Python sidecar (JSON-RPC over stdio)     all audio analysis and file audio work
    +--->  External tools (ffmpeg, fpcalc, mp3gain bundled; yt-dlp as a Python module)
    +--->  claude CLI (`claude -p`, headless)       style, mood, prompt parsing
    +--->  Online lookups (AcoustID, MusicBrainz, Discogs, iTunes, Cover Art Archive)
    +--->  Library files on the external drive
    +--->  Rekordbox XML (written and read; Rekordbox itself is driven by the user)
```

- The user only ever interacts with the renderer.
- The renderer has no Node access. It never touches files, the database, the network or a process. Everything goes through `window.api`.
- Python is called only by the main process, through one bridge.
- The app never talks to Rekordbox directly: it writes an XML the user imports and reads an XML the user exports.

SQLite: `src/main/db/` holds one connection (WAL mode, foreign keys on) opened at startup, the Drizzle schema and the query functions. The file lives at `app.getPath('userData')/fixlibrary.db`. Applied migrations are never edited; every schema change is a new migration.

- Startup opens the database and runs the pending migrations before IPC, the sidecar and the window. If the database cannot be opened or migrated, or was written by a newer version of the app, the app shows an error and quits. Only one instance of the app runs at a time.
- Migrations run with foreign keys off (a table rebuild would otherwise cascade into the child tables), followed by a foreign key check; the keys are on for everything else.
- Rows that undo depends on never disappear as a side effect (the same holds for `batch_files`): a batch with backups cannot be deleted, a track that a batch refers to cannot be deleted, and deleting a track only clears the link on its backup rows. The one delete of batches is `deleteDiscardedBatches`, run when a new run starts: it removes batches that were cancelled before anything was written (never applied, no backup, no apply job ever started), with their items and jobs. A batch that got as far as writing is never deleted by it.
- Track paths are stored normalized and NFC-composed, and the volume name is always derived from the path.
- Settings keys that start with `secret.` are reserved for encrypted values (task 6); `setSetting` refuses them.
- Migrations are generated with `npx drizzle-kit generate --name <what_changed>` and committed. The packaged app reads them from `Resources/migrations` (`extraResources`).
- Query functions take the database as their first argument, so tests run them against a temporary file built by the real migrations (`src/main/db/database.test-util.ts`).
- JSON columns are typed `unknown` in the schema and validated with Zod by the query function that reads them.
- A track stores the name of its volume (`/Volumes/<name>`), or null on the startup disk. Queries return `offline: true` for a track whose volume is not in the set of mounted volumes (`services/volumes.ts`, which counts mount points only, not leftover folders); an offline track must not be processed.
- End-to-end tests start the app with `--user-data-dir` pointing at a temp folder, so they never touch the developer's database.

Where new code belongs:

- A new screen: `src/renderer/pages/<Name>.tsx`. Thin. Calls `window.api`.
- A new renderer-to-main call: add the channel and types to `src/shared/ipc.ts`, expose it in `src/preload/index.ts`, register the handler in `src/main/ipc/<domain>.ts`.
- New business logic: `src/main/pipeline/<domain>.ts`, as pure as possible.
- A new pipeline stage: `src/main/pipeline/stages/<stage>.ts` implementing the `Stage` interface.
- Anything that touches a file, process, network or the database: `src/main/services/` or `src/main/db/`, imported by a pipeline module, never by `ipc/` handlers directly for writes.
- New audio work: an `@rpc` method in `python/fixlib_py/`, with its types added to `src/shared/rpc.ts`.
- A new UI primitive: `src/renderer/components/ui/`, added to DESIGN_SYSTEM.md in the same commit.

## 04 Data flow

Request path for every user action:

1. Component calls `window.api.<domain>.<method>(…)`.
2. The IPC handler in `src/main/ipc/` validates the payload with Zod.
3. A pipeline function applies the rule, calling services, the database and the Python bridge.
4. A typed result returns. Long work reports through `pipeline:progress` events instead.
5. The renderer store updates from the response or event, not from a guess.

Every batch has two phases:

- **Compute**: analysis, lookup, proposals. Results go to `batch_items` and the analysis cache. No library file is modified.
- **Apply**: runs only after the user approves the batch preview. All file changes go through `services/file-ops.ts`: backup or copy first, write to a temp file in the same folder, then rename.

State:

- Durable state lives in SQLite. Jobs, batches and the full-run state machine are resumable after a restart.
- Renderer state is UI state plus a cache of what main returned. Main is always the authority.
- Optimistic updates: none in v1.

External tools:

| Tool    | Version    | How it gets here                                                                 | Licence                    |
| ------- | ---------- | -------------------------------------------------------------------------------- | -------------------------- |
| ffmpeg  | 9.0.2      | built from the ffmpeg.org source by the script, with LAME 4.0 linked in          | LGPL 2.1 or later          |
| mp3gain | 1.6.2      | built from source by the script, with libmpg123 1.33.7 linked in                 | LGPL 2.1 or later          |
| fpcalc  | 1.6.1      | official Chromaprint `macos-arm64` release binary                                | MIT, with LGPL FFmpeg code |
| yt-dlp  | 2026.08.19 | Python package in the sidecar environment (`python/uv.lock`), run as `-m yt_dlp` | Unlicense                  |

- `scripts/fetch-binaries.sh` installs ffmpeg, mp3gain and fpcalc into `resources/bin/`, with their licence texts and a `NOTICE.txt`. Every download is checked against a pinned SHA-256 before it is used. The source pins equal the hashes Homebrew publishes for the same URLs; the fpcalc pins are the digests GitHub publishes. Every tool must contain an arm64 slice and may link only against system libraries. The build ignores Homebrew and the caller's compiler settings, so it needs only the Xcode Command Line Tools.
- ffmpeg is deliberately small: audio only, the formats the app converts between, `file` and `pipe` as the only protocols. It is not the `ffmpeg-static` build the plan named: that binary is compiled with `--enable-nonfree` and may not be redistributed. A new format or filter means a new configure flag in the script. The mp4 muxer is built in for its options only, by the owner's choice (T-034): yt-dlp passes `-movflags +faststart` to every conversion it runs, and ffmpeg refuses an option no muxer of its build knows; SoundCloud's AAC streams also need it to be put in an M4A before they are converted.
- The script records the SHA-256 of every installed file. `./scripts/fetch-binaries.sh --verify` checks them, and `build:mac` and `build:unpack` run it first, so packaging stops if a tool is missing or was changed.
- yt-dlp is not a bundled binary. The official single-file build unpacks itself on every start (20 s per call on an M1, against 0.1 s as a module), and electron-builder cannot sign the folder build. As a Python package it is pinned and hash-checked by `uv.lock` like every other dependency. Task 43 therefore updates a Python package, not a file in `userData`.
- `services/binaries.ts` is the only place that knows how to start the tools: `resources/bin/` in development, `Resources/bin/` in the packaged app, and the sidecar's interpreter with `-I -m yt_dlp` for yt-dlp. Nothing falls back to a tool on the PATH. `checkAll()` runs each tool with its version switch, an empty environment and a neutral working directory, and returns a version or a reason code, never raw output.
- Not verified in the packaged app: it has no Python runtime before task 41, so yt-dlp is reported as missing there, and the packaged app itself does not start yet because of its signing settings (task 42).
- Rules for the code that will call the tools with untrusted input:
  - ffmpeg: `-nostdin`, an absolute input path, the input format forced with `-f` from the app's own check of the file, and an app-generated output name. Tag text never goes into a filter string.
  - yt-dlp: the URL is validated in the main process (`addressOf`: https or http, the hosts of YouTube and SoundCloud only, no credentials, no port) and passed after `--`; always `--ignore-config`, `--no-plugin-dirs`, `--use-extractors youtube.*,soundcloud.*`, `--no-cache-dir`, `--no-playlist` and an explicit `--ffmpeg-location`; never `--exec`, `--cookies-from-browser` or `-U`. It runs with a `PATH` of system folders and nothing else in its environment, in its own process group, so a stop also ends the ffmpeg it started.
  - mp3gain: always `-s s`, absolute paths, and only files the app has identified as MP3.
  - All of them: an argument array, an explicit minimal environment, a timeout.

Settings and secrets:

- `src/shared/settings.ts` holds the schemas and the defaults. Settings are stored as six groups, one row each; a group that was never changed has no row, and a folder that was never chosen is null. `pipeline/settings.ts` resolves the value in use (backup folder next to the library, Rekordbox folders under `~/Documents/FixLibrary`, worker count one less than the CPU cores and never more than the cores). A library that is a whole drive or a home folder has no folder next to it that the app could create, so it has no default backup folder: the user has to choose one.
- The `analysis` group holds the tempo range (`bpmMin`, `bpmMax`, 85 and 175 by default). Its two ends are whole numbers, are saved together, and must hold a whole octave (`bpmMax` at least twice `bpmMin`), so every tempo has exactly one place in the range.
- The renderer changes settings with a typed, validated patch. There is no generic "set key to value" call, an unknown key is refused, and the merged result is validated again before it is written.
- Folders are never accepted from the renderer: `settings:pickFolder` opens the dialog in the main process, which also words the dialog, and stores what the user picked as the file system names it (links resolved). The library, its clean copy and its backup folder may not contain one another; this is decided by what the folders are on disk, not by how their paths are spelled. A folder that does not exist yet is resolved as far as it exists and compared by spelling from there on. The rule is checked when a folder is chosen; the tasks that write files check their targets again when they run.
- API keys are encrypted with Electron `safeStorage` (a key in the macOS Keychain) and stored under the reserved `secret.` keys of the settings table. Without the Keychain a key is not stored at all. A key's value never goes to the renderer, only where it comes from: stored, the development env file, unreadable, or missing.
- In development `.env.local` is a fallback for keys that are not stored. Only the three key variables are kept, in an object and never in `process.env`, so child processes cannot inherit them. The packaged app does not read the file.
- The app is ad-hoc signed, so the Keychain item belongs to one build. After an update a stored key may not decrypt; the Settings page then shows it as unreadable and asks for it again.
- A key test is a real request with the owner's key: one at a time per service, and no second request to a service within five seconds, whatever is saved or deleted in between (a test that comes too soon is answered without a request). It never follows a redirect. Only a clear answer counts; anything else is reported as "not checked". A result belongs to the keys it was run with: once a key changes, a test that ran or is still running with the old one is not reported for the new one.
- A stored key is encrypted together with its name, so a ciphertext copied to the row of another key is not accepted there.
- Names of styles and hot cues are stored composed (NFC) with single spaces. Control, invisible, private-use and unassigned characters are refused, which also rules out emoji sequences that need a joiner.
- A style that a track uses cannot be deleted; `Unsorted` always exists and keeps its name.

IPC handlers:

- Every handler is registered through `handleIpc` (`src/main/ipc/handle.ts`). It runs the handler only for the app's own page (the main frame, at the renderer's URL) and only with arguments that fit a Zod schema. Anything else is rejected with a fixed message and logged by channel name. A handler that throws is logged in the main process, and the renderer gets a fixed message, never the error text. In development every page of the dev server's origin counts as the app's page.
- The main process tells the renderer something unasked only on the channels of `IPC_EVENTS` in `src/shared/ipc.ts`. The preload exposes each as a subscribe function that hands the page the payload alone and returns the function that unsubscribes. Progress goes out at most four times a second (`ipc/progress.ts`).
- Calls that can fail in an expected way return `Result<T>` from `src/shared/errors.ts` (`{ ok, value }` or `{ ok: false, code }`), because an error thrown across IPC loses its code. The renderer maps the code to Hungarian text.
- The window's top-level document cannot navigate away from the app's page, and no webview can be attached. A frame inside the page gets no preload and is refused by the handlers.

Library scan:

- `pipeline/scanner.ts` walks the library folder and keeps the `tracks` table in step with it. It only reads: no library file is changed, moved or deleted by a scan. It runs when the app starts (if a library folder is chosen) and from the Library page; one scan runs at a time, and a second request joins the one that is running. `library:followScan` gives the page the result of a running scan without ever starting one.
- The walk takes `.mp3`, `.wav`, `.aif` and `.aiff` files in any letter case. It skips every entry whose name starts with a dot (hidden files, `._*` AppleDouble files, `.Trashes`, `.Spotlight-V100`, `.fseventsd`), never follows a link, and leaves out the backup and clean library folders.
- A track stores the size and modification time of its file as last scanned. A file with both unchanged is not read again. New and changed files go to the sidecar's `tags.read` in batches of 50 (`TAG_BATCH_SIZE`), which returns duration, bitrate, sample rate, the basic tags and whether a cover is embedded. A file that cannot be read is listed without tags, with `stageStatus.scan` set to `failed`.
- A file that is gone is marked `fileMissing`; its row stays, because batches and backups may refer to it. Nothing is marked missing when a folder could not be read, or when the library is not reachable at the end of the scan.
- Before it starts, and again before it marks anything missing, the scan checks that the folder is there and, for a path under `/Volumes`, that the volume is mounted: an unclean eject can leave an empty folder behind. A drive that goes away ends the scan with `LIBRARY_UNAVAILABLE`; what was stored until then stays.
- The home folder, anything above it and `/Volumes` itself cannot be the library (`LIBRARY_ROOT_UNSUITABLE`). This and the rule that the library folders may not contain one another are checked when a folder is chosen and again by every scan.
- A file that could not be read (`stageStatus.scan` is `failed`) is tried again by every scan, whether it changed or not; if it is still unreadable, the scan counts it as unchanged. A file whose read ran out of time is `skipped` instead and is not tried again until its size or modification time changes, because trying it costs minutes.
- When a whole batch fails, its files are read one by one, so one file the sidecar cannot cope with is recorded as unreadable instead of stopping every scan at the same place. After a single file fails, the sidecar is asked whether it is alive (`ping`): if it answers, the file was the cause; if not, the scan ends with the sidecar's error.
- Every entry of a `tags.read` answer is validated on its own (`fileTagsSchema`). An entry that does not fit makes that one file unreadable; an answer about other files than were asked for ends the scan.
- The sidecar chooses the parser by the file's extension, never by its content, and opens the file itself: nothing reached through a link in any part of the path (`O_NOFOLLOW_ANY`), regular files only. No single read may exceed 16 MB, which bounds a tag, a cover and a WAV or AIFF chunk alike. Tag text is cut to one line of 300 characters without direction marks; with that limit the largest answer for a batch fits the 1 MiB line limit of the bridge.
- Not covered: a compressed ID3 frame inside the read limit can inflate to much more memory, and a tag of very many tiny frames can take minutes to parse. Such a file is read once, runs into the batch timeout and is then `skipped`, but its sidecar thread works on until it is done. Parsing in a process that can be stopped would close both.
- A scan that could not look at part of the library (a folder it may not read, an entry that vanished, a library that had tracks and shows no file at all) reports `complete: false` and marks nothing missing. `missing` in the result is the total of this library's tracks without a file, not only the ones this scan noticed.
- Known limit: a file renamed only in letter case is a new track to the scan, and the old row is marked missing.
- A path is stored composed (NFC), but a file is always opened by the name the disk gave during the walk.
- The scanner reads the file system itself instead of going through a service: it only lists and stats, and `services/file-ops.ts` stays the only code that changes a library file.

Library page:

- `library:list` returns one page (at most 500) of `LibraryTrack` rows in path order: what the table shows of a track and nothing more. The page loads all of them into `stores/library-store.ts`; search, filters and sorting are pure functions in `renderer/lib/library-view.ts` and run in the renderer, which is fast enough for the 3000 tracks the app is built for and makes range selection and "select all" trivial. The table itself is virtualized (`@tanstack/react-virtual`).
- The selection (`renderer/lib/selection.ts`) lives in the store as a set of track ids. A search or filter that hides a selected row takes it out of the selection, so a run never processes a track the user cannot see selected; sorting keeps the selection. Tracks that are gone leave it when the rows are loaded again after a scan.
- `library:run` takes track ids, or the whole library, and nothing else. `pipeline/library.ts` decides which of them a run may process: a track that is offline, whose file the last scan did not find, or that is not in the library is left out and counted. A track whose tags could not be read is not left out: its audio may still be fine. File and folder names are sent to the page as one clean line, for display only; the page never sends a name or a path back. The mounted volumes are looked up at most once a second for these calls, so one load of the table sees one state; the scanner always asks afresh. Until the orchestrator exists (T-009) the handler only answers with those tracks; nothing is processed.

Pipeline runs:

- A stage (`pipeline/stages/stage.ts`) is one step for one track: a name, a phase (`compute` or `apply`), the resource it needs, the stages it depends on, a timeout and `run`. `pipeline/stages/index.ts` lists the stages and checks at startup that they can be ordered: no circle, no unknown or duplicate name, no compute stage that waits for an apply stage. The stages are made by `createStages`, which hands them the database, the sidecar and the settings they read; `bpmKey` (T-013) is the first.
- A run is a batch: one `batch_items` row per track, holding the track as it was (`before`) and what the stages propose (`after`), and one `jobs` row per track and stage. Asking for a stage adds the stages it depends on. Only a track that is in the library, online and has its file becomes part of a batch; this is decided when the run starts, whatever the caller checked.
- `pipeline/orchestrator.ts` runs the jobs. A job starts when the stages it depends on are done for the same track, and when its resource has room (`pipeline/queue.ts`): `cpu` is the worker count of the settings, read again whenever a job could start; `gpu` 1, `claude` 20 (as many jobs as one call to Claude holds items; the calls themselves go one at a time), `io` 2, `network` 4.
- A job goes through `pipeline/run-stage.ts`, so a failure or a timeout becomes a `TrackError` on the job and on the item of the batch (the first error of a track stays). The jobs that wait for a failed one are skipped; the other tracks go on.
- Two phases. Compute ends with the batch in `preview`: nothing was written, and the apply jobs stay queued. `applyBatch` starts them, only for the items the user approved and did not take out, and ends with the batch `applied`. Only one batch waits for approval: starting a new run cancels an older one, and deletes it together with every other batch that was given up unwritten, so the rows of runs that came to nothing do not pile up.
- One batch is computed or applied at a time; a second start is answered with `RUN_ACTIVE`.
- Pause: no new job starts and the running ones finish; the pause and its reason are stored on the batch. If the drive of a track is not mounted when its job would start, the run pauses itself (`offline`) instead of failing every track that is left.
- Cancel ends the batch at once: in one transaction the batch becomes `cancelled` and every job that is not over becomes `skipped`, the running ones included. They get their abort signal, and whatever they still return is thrown away. A cancelled batch is never taken up again. A stage that writes files must therefore stop on its signal: a write that finishes after the cancel is not recorded on the job.
- Restart: quitting tells the running jobs to stop and puts them back in line. At the next start the batch that was being computed or applied is taken up again: `done` jobs are not run again. A batch the user paused stays paused; one that had paused for a missing drive goes on, and pauses again if the drive is still away. After a crash the jobs that were running go back in line too, but the start counts: a job that was running in three crashes is recorded as failed, so a file that makes the app crash cannot do so forever.
- The apply phase never writes a track that a stage failed for, approved or not.
- What listens to a run (progress, the sleep blocker) cannot stop it by failing, and may act on the run from inside a report: the last report of a run goes out after the run is over.
- A run is started from the Library page with `library:run`: track ids, or the whole library, and the names of the functions to run. Only the names of stages marked `selectable` are accepted; the stages they depend on are added by the orchestrator. At most one run is started in two seconds, and pause and resume are acted on at most four times a second, so a page cannot fill the disk or the log by calling in a loop. `pipeline:state` tells the page which functions exist and which run is active; `pipeline:pause`, `pipeline:resume` and `pipeline:cancel` take no argument and act on the one active run.
- `pipeline:progress` events go to the page at most four times a second. A report that says something new about the run itself (paused, went on, ended, another batch or phase) is never held back, and the newest report that was held back still goes out when its time has come: a run may stand still for minutes, and the page must not show old numbers all that time. A report carries the time the run has worked (pauses do not count) and how many tracks failed.
- While a run works, `services/power.ts` holds off sleep with Electron's `powerSaveBlocker` (`prevent-app-suspension`); a paused run with nothing running lets the Mac sleep.
- At startup the app scans the library first and then takes up a run that was interrupted, so both do not read the drive at once. Until then the run is not shown, and a new run is refused. The limits of the resources are read from the settings at most once a second. Quitting calls `shutdown` on the orchestrator before the sidecar is stopped and the database is closed.
- Long work in the sidecar runs inside `cancellable(job_id)` and checks its stop event between steps. The bridge takes a job id and an abort signal with a call: on abort the call is rejected at once and `job.cancel` is sent. A job has five seconds to stop. A cancel that reaches the sidecar before its job has registered is remembered, and the job is stopped as it starts. Every attempt of a job gets its own id, made in the main process, of at most 64 characters. No method uses this before T-013.
- In development, `FIXLIB_DEMO_STAGES=1` puts stand-in stages in the place of the real ones (`pipeline/stages/demo.ts`): they read no audio and only wait, so a run can be tried and tested end to end in seconds, on files that are no music; `FIXLIB_DEMO_STAGE_MS` sets how long they take. The packaged app ignores both.
- Progress is reported as counts per stage and an estimate of the time left: per stage, how long its last 50 jobs took, times the jobs left, over how many run at once. There is no estimate while a stage with jobs left has not finished one.

File changes, backup and undo:

- `services/file-ops.ts` is the only code that copies, renames, overwrites or deletes a file of the library. It knows nothing about batches. Every write goes through a temp file next to its target (`.<name>.<8 hex>.fixlib-tmp`, a new name per write), which is synced to disk and renamed into place only when it is complete; a write that fails or is told to stop leaves the target byte-identical and removes the temp file. A file gets a new name through `link` and `unlink`, which fail if the name is taken: a move or a copy never replaces another file, also when two of them race for one name. Only `restore` and `replace` write over an existing file. It refuses a path that is not absolute and plain (no `..`), and every path whose nearest existing folder is not inside the library, the clean library or the backup folder, decided by what the folders are on disk and not by spelling. Links are resolved first, so a path through a link that points out of those folders is refused; a source that is itself a link is refused too. It never deletes a folder that holds anything, and never one of the three folders.
- `pipeline/batch-files.ts` holds the rules. An apply stage gets `context.files`, bound to its one track: `workingPath`, `move`, `replaceContent` and `wouldMove`. `wouldMove(name)` answers whether giving the file a name would change anything on disk, and makes no backup and no copy: a stage asks it first, so a track that needs nothing costs nothing and its batch does not count as one that wrote, which would take away the undo of the batch before it. It is false also for a file that keeps the ` (2)` of a collision while its plain name is still taken; true in the clean library for a track that has no copy there yet, because the clean library holds every track a batch was approved for; and it throws what `move` would throw, and when the file is not there. It takes a name and nothing else: anything with a path in it is refused before any answer is given. `ensureCleanCopy` makes the copy in the clean library for a track that has none there yet, and does nothing in place: the stage that writes calls it first, so the clean library holds every track a batch was approved for, also one that keeps its name or gets no name at all. A backup that was made stays until the batch is undone or a later batch is applied, also when the change it was made for fails: nothing decides that a file is "still as it was" and takes its backup away. A batch whose only change failed on disk therefore counts as one that wrote, which costs the undo of the batch before it; a backup too few could not be made good. A name counts as another track's in any letter case and Unicode form, folded as near to the disk's own comparison as can be told (`findTrackIdsWithName`: compatibility forms and both directions of case, so `ß` and `ss` are one), since on the disks a library is on those are one file. The folder is compared as it is stored. A compute stage gets `null`, so it has no way to change a file. The stages of one track take turns at its file, and every new name is picked and taken under one lock, so two tracks that want one name get two names. `move` accepts only names a library file may have (`unusableNameReason`: an audio extension, no leading dot, no control characters, composed Unicode) and renames nothing once its stage was told to stop. The rule is applied to what is new, as it was asked for: the file name, and the folders that do not exist yet. A folder the file is in already keeps the name it has (`R.E.M.`, a name stored decomposed, one that holds `?`), so a file in it can be renamed. Another folder that exists may be named as it is, but a move into a hidden folder, or one whose name holds an invisible character, is refused: a file in `.Trashes` would be gone from every scan. A file that has the wanted name under another spelling is a name that is taken, which gives ` (2)`, not a name that is wrong. That the target lies inside the library is checked apart from the names.
- In place: before the first change of a track, the original is copied to `<backup folder>/<batch id>/<track id>.<ext>` and recorded in `backups`. The copy is a clone where the file system makes one and a plain copy elsewhere (`COPYFILE_FICLONE`, with `COPYFILE_EXCL` so that nothing already at the temp name is written through). A file that is in the place of the backup without a record is left alone, and the backup is made beside it under the next free name. Every copy is checked by size. A track is backed up once per batch, as it was before the batch; if that backup is gone when the track is taken up again, the track is changed no further.
- Clean library: the first change copies the track to the same relative place under the clean library folder, and all work happens on the copy. The track's `path` then names the copy and `originalPath` the untouched original; the scanner knows such an original and does not take it for a new track. A copy that an earlier batch made is backed up like an original before a later batch changes it.
- `batch_files` is a journal of the files a batch creates (copies, and files under a new name), kept in the one spelling a track's path is stored in (composed), whatever the folders are spelled like on disk: undo knows a file of the batch by comparing the two. A row is written before its file is, so undo and the next run know about a file even if the app stopped between the two; a row whose file was not created after all is removed again. After a crash, a file that is not where its track says is found again through the journal.
- A taken name gets ` (2)`, ` (3)`, …; the stage is told, and reports `NAME_COLLISION` for the preview.
- Before the apply phase starts, `checkSpace` adds up what still has to be copied, per volume, and `applyBatch` answers `NOT_ENOUGH_SPACE` if that plus 64 MB does not fit. The whole size is always counted, also where a clone would take no room.
- Undo (`undoLast`) acts on the newest batch that changed files and has not been undone, also one that was cancelled halfway. It plans and checks everything before the first file changes: every record of the batch is readable, every backup exists and lies in the backup folder, every place a file goes back to lies in the library or the clean library. If a check fails, undo changes nothing. Then it puts each backup back in one step per file, deletes the file the batch left under a new name (only the track's current file, and only if the journal names it; a file that only got another letter case is renamed back), restores the tracks whose files it touched from `batch_items.before`, marks the batch `undone`, deletes the backups it has put back, and cancels a batch that waits for approval, since its proposals were made for other files. A track without a backup is only ever the copy a clean library batch made: its copy is deleted if the original is still there, and kept with its track if not. In place, a touched track without a backup record makes undo refuse the whole batch. An undo that stopped halfway and is asked for again knows the files it has already put back (the track's file is gone, and the file at the old name is as big as the backup). Undo never writes over a file that is not the track's own: if the old name is taken, the original goes back under the next free name. The path of a restored track is where its file really went, not what the record says. It is refused while a batch is computed or applied, and it can be asked for again if it stopped halfway.
- Once a batch that wrote files is applied, the backup files and records of every earlier batch are deleted: only the last batch can be undone, and a library's worth of backups must not pile up. A batch that wrote nothing deletes nothing, so the last batch that did write stays undoable. Only a file inside the backup folder is deleted as a backup, whatever a record says. An apply or undo that is asked for while backups are being deleted, or while a stage of a cancelled batch is still finishing a copy or a rename, waits for that to end.
- A scan and a change of files never run together: the scanner starts no scan while a batch is applied or undone (`RUN_ACTIVE`), and `applyBatch` and `undoLast` are refused during a scan and until the startup work is over.
- The backup folder in use cannot change while a backup exists (`BACKUPS_IN_USE`), also not by moving the library when the folder is the default one next to it: undo reads the backups from there.
- At startup the app deletes the `.fixlib-tmp` files that interrupted writes left in the three folders, before it scans. The cleanup follows no link and stays on the volume of the folder; a file it cannot remove is logged and the rest is cleaned all the same.
- Before every scan, the one at startup and one asked for later alike (`beforeScan` of the scanner), the tracks of the last batch that wrote are told where their files are (`reconcileInterrupted`): where the app stopped between giving a file its new name and writing that down, the journal names the file. A scan would otherwise take such a file for a new track and its track for missing. It looks only at tracks whose step in that batch did not end: a step that ended has written down every name it gave, so for a finished track the journal is history, and a file that sits under one of its old names today is somebody else's (taking it would hand it to undo, which deletes what a batch created). It changes no file, skips a track whose drive is away, and does not take the journal at its word: only a plain file in the library or the clean library, of the size the track has, which no other track has under any spelling, becomes a track's file. A track that is not found is counted in one log line. Any other failure, a database that is closed above all, fails the pass, and then the scan does not run. A recovery is also refused when the folders were changed in Settings since the batch ran.
- Quitting waits for the file step a stage is in (`waitForFileWork`, at most 30 s) before the sidecar is stopped and the database is closed: a stage that was told to stop still finishes its rename or its write and records it. After the time is up the app quits anyway and says so in the log; the next start then puts the track right from the journal. Each step of quitting is tried on its own, so one that fails does not keep the next from running; with no sidecar and no file work the app quits at once, as before. A crash during the wait does not start the app again. An undo and the deletion of older backups count as file work too. An undo is waited for without a limit: it puts many files back and writes all of that down in one step at its end, so cutting it short would leave files restored that the database does not know of. The window stays open until it is done; what else is still going on then gets the 30 s. No scan starts while the app is quitting. A second undo, or an approval, that is asked for while an undo is under way is refused at once (`RUN_ACTIVE`), not queued behind it.
- `applyBatch` and `undoLast` are reached from the page only through the batch preview (`preview:approve`, `preview:undoLast`), described below.

Batch preview:

- What a stage proposes for a track is a `Proposal` (`shared/preview.ts`): `fields`, each with a value, its source (`lookup`, `musicbrainz`, `discogs`, `id3`, `analysis`, `claude`, `manual`) and an optional confidence, and `warnings`. It is stored in `batch_items.after` and read through its schema field by field, so a field or warning that is unknown or not valid is neither shown nor passed to an apply stage, and the others stay. A stage may store other keys of its own next to them for its apply stage; they are kept and ignored by the preview. The preview fields are `fileName`, `artist`, `title`, `mix`, `album`, `label`, `year`, `bpm`, `key`, `styleId` and `energy`; a task that needs another one adds it to the schema. A tempo is a whole number, a key one of the 24 Camelot codes.
- `pipeline/preview.ts` builds a `PreviewRow` per item: every field before and after, whether it changed, its source and confidence, the warnings, the exclusion and the error. `LOW_CONFIDENCE` is derived here, for a change proposed with less than 70% confidence; the other warnings (`DUPLICATE`, `NAME_COLLISION`, `LOW_BITRATE`, `CANNOT_NORMALIZE`, `UNSORTED`) are reported by stages. A stage names the warnings it reports (`warnings`); when it proposes again after an edit, those are replaced by what it reports then.
- Editing (`preview:edit`): one of `artist`, `title`, `mix`, `key`, `styleId`, `energy`, validated by the same schema as a proposal, stored with the source `manual`. Then every compute stage of the batch that has a `recompute` function proposes again from the fields as they are now (a new title gives a new file name); `recompute` is pure and quick, and a manual field is never written over by it. The row comes back as it is afterwards.
- A field the user set by hand is protected twice: within the batch by its `manual` source, and after the batch by `tracks.locked_fields`. Once every apply stage of the batch is done for a track (`onTrackApplied` of the orchestrator, `commitApprovedValues`), the manual values of that track's row are written to the track and their names added to `locked_fields`; an approved track the batch has nothing to write for gets them when the apply phase starts. The same step writes the proposed tempo and key to the track (`bpm`, `camelot_key`, `musical_key`), whatever proposed them: they are measured from the audio and need no file to be written, so they have no apply stage. They are locked only when the user set them by hand. When a later run merges the proposal of a stage, fields in `locked_fields` are left out, and a rescan does not replace a locked artist or title with the file's tags (the manual value reaches the tags only once a stage writes them). A batch that is given up locks nothing, and neither does a track whose apply stage failed or never ran: its row never says more than its file. Undo puts the old values and locks back for the tracks whose files the batch touched. There is no way yet to take a lock off by hand.
- Approval (`preview:approve`): marks as approved every row that was not taken out and did not fail, checks the free space (the answer carries the needed and free bytes for the page), and calls `applyBatch`. While an approval is on its way nothing else may change the batch. `preview:discard` ends the batch as cancelled.
- An apply stage gets `context.proposal`: what the batch holds for its track, with the user's edits. A stage that writes (apply phase, not selectable) joins a run by itself once every stage it depends on is in it: the user asks for a function, not for the step that writes its result.
- The page loads all rows of the batch in pages of 500 into `stores/preview-store.ts`; the filters ("Csak figyelmeztetések", "Bizonytalan", "Duplikátumok", "Hibák") are one pure function in `shared/preview.ts` and run in the renderer. The store shows a change only after the main process has taken it.
- `components/features/preview/BatchPreviewTable.tsx` is the one table: virtualized, with a cell cursor, in-place editors and the exclusion checkbox. It knows nothing about what a column shows. The column sets live in `components/features/preview/preview-columns/`, one file per kind of batch (`run.tsx` today, `errors.tsx` for the "Hibák" tab); tasks 15, 19, 21, 24, 32 and 34 add theirs there.
- The folders of the library cannot be changed while a batch is computed, waits for approval or is applied (`RUN_ACTIVE`).
- The table's wide-only columns (label, year, source) never make it scroll sideways: they join in the order they are defined, each only where the table still has room for it.
- Asking again (`preview:refreshLookup`): for one row of the batch that waits, every stage of the batch that is marked `refreshable` runs once more with `context.refresh` set, through `run-stage.ts` and its time limit. What it proposes is merged like the result of a run (what the user set by hand stays), the warnings the stage owns are replaced, and the stages with a `recompute` propose again. Before the new answer is merged, what the stage proposed before for the fields it names (`proposes`) is dropped, so a row never mixes two answers; the lookup also says outright when it has no ids. One row at a time and at most one in two seconds; while a row is asked about, nothing else may change the batch (`RUN_ACTIVE`). A refresh that fails leaves the row as it was and is no error of the track. `PreviewBatch.canRefresh` tells the page whether the batch ran such a stage.
- In development, `FIXLIB_DEMO_STAGES=1` puts three stand-ins in the place of the real stages: two that propose a made-up artist, title, energy and file name, and one apply stage that renames the file to the proposed name through the normal backup and undo. That stage works only on files under the system's temp folder or in `tests/fixtures/synthetic/` (`isGeneratedFile` in `src/main/index.ts`); for any other file it fails the track and renames nothing.

Names and file names (T-015):

- A name the user set by hand is neither changed nor taken apart (`keep` of `cleanNames`): its mix and its guest stay where the user put them. With a mix known already, only its double is taken out of the title; another version named there stays, so two versions never get one name. Input is cut to 1000 characters before the patterns run, and `cleanNames` gives the same result when it is run on its own result.
- `pipeline/naming.ts` is pure: `parseFileName` (what a file name says by the usual patterns: `Artist - Title`, `01. Artist - Title`, `Artist_-_Title`), `cleanNames` (junk out, `ft`/`feat`/`featuring` to `feat.`, a guest named in the title to the end of the artist (in brackets in any spelling; in the open only as `feat.`, `ft.` or `featuring`, because a bare `ft` or `feat` is as often a word of the title: `Trip to Ft Lauderdale`; a guest ends at the next bracket or at a dash between spaces; a guest the artist names already, as a whole name, is not added twice), a mix named in the title to the mix) and `formatFileName` (`Artist feat. X - Title (Mix) [8A Am - 124 - E7].mp3`; the tempo and the energy are left out while they are not known, so the energy joins the name once T-024 computes it; without a key there is no bracketed part at all, because the part is known again by the key it starts with).
- `shared/junk-patterns.ts` holds what is thrown out. Every pattern is narrow on purpose: a word such as "Audio" or "Lyrics" is junk only as a whole bracketed phrase, a track number only with a dot, a bracket, a dash or a leading zero (`50 Cent` and `2 Unlimited` stay), a vinyl side (`A1 `) only in front of `Artist - Title`. A bracketed part that names a mix (`Original Mix`, `X Remix`, `Radio Edit`) is kept. What the app itself wrote at the end of a file name (`[8A Am - 124 - E7]`, recognised by its key, with the ` (2)` of a collision after it) is taken off when the name is read again, so a file is not given the part twice: naming a file the app has named gives the same name.
- What a file system refuses is replaced when the name is built: `/`, `:`, `\`, `|`, `*`, `<`, `>` become `-`, `"` becomes `'`, every kind of space becomes a plain one, `?` and invisible characters go, a leading dot goes, the name is composed (NFC). The plan names only `/` and `:`; the others are refused by exFAT, which external drives often have.
- Length: a name holds at most 220 UTF-16 units (`MAX_FILE_NAME_LENGTH`, the rule the rename applies) and at most 228 UTF-8 bytes, a careful limit for file systems that count a name in bytes, with room for ` (999)` after a collision and for the temp name of a write. A longer name loses the end of its title, then of its artist, cut by whole characters; the bracketed part and the extension always stay.
- The compute stage `naming` (selectable) waits for `lookup` and `bpmKey`, so asking for it runs all three. It cleans the artist, title and mix the batch holds (from the lookup, else from the tags; without a title, from the file name, with the source `fileName`) and proposes them where they change, keeping the source and confidence they had. The file name it proposes has the source `naming`. A name the user set by hand, in this preview or an earlier one, is taken as it is. Its `recompute` builds the name again after an edit, without cleaning what the user typed.
- The apply stage `rename` (`io`, not selectable, waits for `naming`) gives the file the proposed name in the folder it is in, through `context.files.move`. It is the first stage that changes a library file. It writes only a name as the naming builds one (`isBuiltFileName`), refuses a name with another extension, and reports `NAME_COLLISION` when the name was taken, also when it is the copy in the clean library that had to take ` (2)` and keeps it. It asks `wouldMove` before it asks for the file, so a track that needs nothing costs no backup and its batch does not count as one that wrote: the batch before it stays undoable. A track whose file is gone fails with `FILE_UNREADABLE` instead of counting as done. The bytes of the file never change.
- As with a lookup, the cleaned names reach the track's row only with the stage that writes the tags (T-016). The new path of the file is recorded at once.

Tag writing (T-016):

- `fixlib_py/tag_write.py` writes ID3v2.3 into MP3 and AIFF files: `TPE1`, `TIT2` (with the mix in brackets), `TALB`, `TPUB`, `TYER`, `TBPM` (whole), `TKEY` (the musical name), and one `APIC` front cover (a 600 × 600 JPEG the app made in its covers folder, named by its name there; T-019). Text is UTF-16, because ID3v2.3 knows no UTF-8. A tag that was v2.4 becomes real v2.3 (`update_to_v23`, the sort names kept), and an ID3v1 tag at the end of an MP3 goes: one file, one answer. A field that is not named stays as it is, and none can be taken away; what only an ID3v1 tag said is carried into the new tag before the old one goes. Frames ID3v2.3 has no place for (a release date, a volume adjustment) do not survive the rewrite. A WAV gets no tags: it becomes an AIFF first (T-018).
- `tags.write(src, dst, fields, jobId)` never changes a file where it is. It makes the temp file the file rules named (new, no link followed, next to `src`), copies the whole file into it, changes the tags of the copy, and reads the copy back: the fields must say what was written, the tag must be v2.3, no ID3v1 left, and the audio byte for byte what it was (the sha256 of everything between the tags of an MP3, or of the one sound chunk of an AIFF, found by a walk that trusts no tag reader). A file whose audio cannot be found whole is refused before it is copied. How long the tag of an MP3 is, the tag says itself, and a rewrite takes its word for it; so an MP3 in whose declared tag four frames of MPEG audio stand in a row is refused too: the tag counts audio as its own, and the rewrite would drop it. Otherwise it fails and removes what it made. `tags.would_change(path, fields)` only reads, and says whether a write would change anything; it refuses the same files, so that no backup is made for a file the write would refuse.
- The tag of the file is untrusted on the way in as well. Every load of a file goes through one reader, mutagen with the frame classes of `safe_files.guarded_frames`, which refuse a compressed or encrypted frame at the moment mutagen would unpack it, and through a reader that allows no single read of more than 16 MiB, also the load before the tags of the copy are changed. An AIFF is loaded without a look for an ID3v1 tag: its last bytes are sound. No second parser looks for the tag: which chunk of an AIFF is its tag is mutagen's to say, every time. One count is made before a load, `safe_files.check_frame_count`: mutagen cuts the tag anew for every frame, so a tag of a million empty frames would keep the sidecar busy for minutes. A tag of more than 5000 frames is refused. That count is a limit on work and decides nothing else: it counts by every rule mutagen could read the tag by (each version's frame header, both kinds of size, with and without unsynchronisation and an extended header) and in every `ID3` chunk of an AIFF, and takes the most. `tags.read` of the scan is not behind it yet. `safe_files.py` holds what `convert.py` and `tag_write.py` share: the temp file a call makes and knows again by its identity, the copy that can be stopped, and those frame classes.
- The apply stage `writeTags` (`io`, not selectable, waits for `naming`, comes after `convertFile` and `setAside` and before `rename`) builds the tags from what the batch holds for the track (`tagsFor`: the proposal with the user's edits, else the track's own value; a value that is not known is not written; a locked field keeps the track's value unless the user typed another in this preview). A copy that was set aside into `_Duplicates` gets no tags and so no backup, by the owner's choice: it waits to be deleted. It asks `tags.would_change` first, so a file that says all of it already costs no backup and its batch does not count as one that wrote. Then `TrackFiles.replaceContent`. The call that writes carries the job id and the abort signal, so a quit or a cancel does not wait it out.
- Once a track of a batch that wrote tags is applied, `commitApprovedValues` makes the names, the album, the label and the year the track's own, unless a field is locked: what a lookup found and the naming cleaned reaches the row only together with the file. Not for a WAV or a copy that was set aside, whose file was not written. The next scan reads the title from the tag, where it carries the mix.
- What a batch wrote is written down. `batch_files.sha256` holds the hash of the content a batch put into a file (`replaceContent` takes it of the temp file and records it for the path of the file in the step that puts the content in place, right before the rename; a write that does not get there leaves the note as it was; `convertTo` for the new file), and a move carries it to the new name. A file the batch only copied or moved has none. `replaceContent` puts the new content only in the place of the content the write read: the file is hashed before the write and again in that last step (`FileOps.replace` takes the step as `naming`), and a file another program changed meanwhile is left with its change, the write failing for the track.
- Undo removes a file only when it is provably the batch's own (`isOwnFile`): by that hash, or, for a file the batch only moved or copied, by holding what its backup holds, or what the original of a clean library copy holds. Any other file under a name the batch gave stays where it is; undo counts it (`left`) and the page says so. This closes what T-017 left open: a file the user put into `_Duplicates` under the name of a copy they deleted is no longer deleted by undo. The name of such a file is not free for another track that undo puts back. The same holds where the batch wrote into a file without moving it: undo writes the backup over it only while it still holds what the batch wrote, or what the backup holds; a file another program has written into since stays, and the original is restored beside it as ` (2)`. That holds whatever the batch wrote down about the track, also nothing: a tag write that failed while the file was changing leaves a backup and no note, and the file is still not written over. Such a file is counted in `left` as well. A link that stands at the old name of a file is a name that is taken, not a reason to refuse the undo: whether the old place is in the library is asked of its folder. What undo found out about a file while planning stands while it acts. A stop between the note and the rename leaves a note of content the file does not hold; undo then goes by the backup alone, and leaves a file that holds neither; rows written before migration 0005 have no hash, so the undo of a conversion that was applied before it leaves the AIFF beside the restored WAV.
- A backup is taken back in one case (`retractBackup`): the first change of a track in a batch failed, the batch has written down no file for the track, and the file holds what the backup holds, byte for byte. The batch then does not count as one that wrote, and the batch before it can still be undone. In every doubt the backup stays. The record goes before the file. The backups of older batches are pruned only after the file work of the batch has ended, so that a step that ran out of time and takes its backup back afterwards cannot leave no batch to undo. Quitting asks again whether file work is going on each time the work it waited for has ended (`waitForFileWork`), so the pruning that begins at that moment is waited for too, within the one time limit.
- The rule against moving a file into a hidden folder now looks at the folder as it is on disk: a link named like any folder that leads into `.Trashes` is refused.

WAV to AIFF (T-018):

- Tags and covers do not work in a WAV in Rekordbox, and a file above 48 kHz does not play on every Pioneer player. `fixlib_py/convert.py` (`convert.wav_to_aiff(src, dst, jobId)`) writes a WAV as an AIFF: 8 and 16 bit become 16 bit, 24 bit stays, 32 bit and floating point (32 and 64 bit) become 24 bit, a rate above 48 kHz comes down to 48 kHz and any other rate stays. The source is read through a descriptor that follows no link. It must say of itself that it is a WAV of plain samples before any parser sees it (`RIFF`…`WAVE`, and a `fmt ` chunk of PCM or floating point, also behind the longer header), libsndfile must agree (`WAV` or `WAVEX`, at most 8 channels, at least one sample), and it is handed to the app's ffmpeg as its standard input with the demuxer and the decoder both named, so the content of a file chooses neither, and with the size of the output bounded by what the header promises; the result is checked before it is returned (an AIFF of 16 or 24 bit, the rate that was asked for, the same channels, the length within 10 ms). A source that is an AIFF such a player takes already is copied as it is, which makes an attempt that is run again harmless.
- Tags: ffmpeg carries the RIFF INFO texts of the WAV into the AIFF as ID3v2.3 (`-bitexact`, so no line names the tool). The frames of an `id3 ` chunk in the WAV, the cover among them, are then copied over them with mutagen and written as real ID3v2.3 (`update_to_v23`: a year is `TYER`, not `TDRC`). The chunk is read before anything is written, once, by mutagen itself, through frame classes that refuse a compressed or encrypted frame at the moment mutagen would unpack it (a few hundred kilobytes can stand for hundreds of megabytes). No second reading of the tag decides: an earlier walk over the frame headers could be made to disagree with mutagen in five ways. A chunk over 16 MiB, one that ends early, one that is no ID3 tag, or one with such a frame makes the conversion fail for the track, with the WAV left as it is. The sort names (`TSOP`, `TSOT`, `TSOA`) are kept although ID3v2.3 does not define them. Frames that have no place in ID3v2.3 (a release date) and frames mutagen does not know are not carried; their ids come back in `tagsLost` and are written to the log for the track. The WAV that held them is in the backup folder until a later batch is applied. The app's own `tags.read` does not see RIFF INFO in a WAV, so after a conversion and the next scan a track may show an artist and a title it did not show before. What `tags.write` will add comes with T-016.
- `dst` is never chosen by the sidecar and never a final name: it must be absolute, next to `src`, and a temp name of `services/file-ops.ts` (`.<name>.<random>.fixlib-tmp`). The sidecar makes the file itself, new and without following a link, and remembers which file it made: ffmpeg writes into it, the tags are added through a descriptor of that very file, and what is removed after a failure or a cancel is only that file. `FileOps.create` then checks that what stands at the temp name is a regular file before it gets a name in the library.
- Two stages. `convert` (compute, selectable, no work on the file) marks a WAV track with the entry `convert` in the `after` of its item and proposes its file name with `.aiff` (source `conversion`); for any other track it proposes nothing. `convertFile` (apply, `io`, not selectable) does the work through `TrackFiles.convertTo`.
- `TrackFiles.convertTo` never lets a file hold content its name does not say. The name with the new extension is taken under the lock of the names, journalled, and kept from every other track while the file is written (`reserved`; `freeNameFor` now picks every name of a batch, the name of a clean library copy included, and counts such a name as taken); the new file is written through a temp file and put in place with `FileOps.create`, which never replaces a file and gives the name inside the same lock; the track gets its new path, format, size, sample rate, bitrate and length; and only then is the old file removed. This removal is the one place besides undo where the app deletes a library file, approved by the owner with this task, on a condition that is checked twice, before the name is taken and again after the new content is written and before it is put in place: every byte of the old file is in another file. In place that is the backup this batch made, a file in the backup folder that holds the same bytes; for a copy this batch made in the clean library it is the original the batch found the track at. A WAV that was changed since its backup, or while it was being converted, or whose original is gone, is not converted and stays. The same is asked a third time at the moment the old file is to go, because syncing a large file to a slow drive takes a while: one that changed in that time stays beside the new file. For a clean library copy the original is the path the batch found the track at; if that file was moved since, the track is refused. A stop between two steps leaves only whole files. At worst the WAV and the AIFF stand side by side with the track on the AIFF, which the next attempt (it removes the old file under the same condition, in place and in the clean library, also when the new file had to take ` (2)`), the scan (`restoredOriginals`) and undo all know what to make of. One gap is open: a kill in the instant between the AIFF getting its name and the track being told leaves an AIFF that the next attempt does not recognise (it converts again into ` (2)`) and that undo leaves; it is a whole file, and a scan takes it for a new track. A track that has the extension already costs no backup.
- Order (`Stage.after`): `naming` comes after `convert`, so the name it builds ends in `.aiff`, also after an edit in the preview (`recompute` is given the item's `after` for this); `rename` leaves a file name of the source `conversion` alone, because the file has that name already and the naming's rule was never asked of it; `convertFile` comes before `setAside` and `rename`. A name the rule for new names refuses is found before the backup is made (`wouldMove`), so such a track costs none.
- The bundled ffmpeg decodes `pcm_f64le`, `pcm_f32be` and `pcm_f64be` as well since this task (`scripts/fetch-binaries.sh`); it has no `lavfi`, so test signals are written with soundfile.

Duplicates (T-017):

- `pipeline/duplicates.ts` is pure, and the check before a download (T-034) is to use the same functions. `findDuplicateGroups`: two tracks are copies of one recording when they have the same AcoustID and the same mix (and, where both lengths are known, lengths 10 s apart at most: one wrong answer of a lookup must not pair a 3 minute file with a 7 minute one), or when their artist, title and mix are the same once normalized (`normalizeName`: lower case, `&` read as `and`, one space, accents kept) and their lengths differ by 2 s at most. Two mixes are never copies of each other; no mix, `Original Mix`, `Original` and `Original Version` count as the same. A match by names needs an artist, a title and a known length. Lengths are measured from the shortest file of a key, so a row of files each a little longer cannot chain into one group; and whatever rules connect them, a group whose known lengths span more than 10 s is cut by length afterwards and the two rules are asked again inside each part, so a file that hung on the group only by a file now in another part is in no group. A file of unknown length joins a group by its AcoustID only when the files of known length under that AcoustID are one group; when a wider group is cut it is asked about with every part, and is left out if two parts claim it. `suggestKeep`: AIFF or WAV before MP3, of two MP3s the higher bitrate, then the longer one, then the lower track id.
- A copy is known only by comparing tracks, and a stage works on one track. So the compute stage `duplicates` (selectable, waits for `lookup`) does nothing per track and has `Stage.regroup` instead: the orchestrator calls it once, when the compute phase of a batch that ran the stage ends and before the batch becomes `preview`, and the preview calls it again after every edit and every refreshed lookup. A `regroup` that throws is logged and the batch is shown without it. It is called once more when a batch is about to be applied. `regroup` says whether it changed anything: the apply is refused with `UNEXPECTED` if it throws then, and with `PREVIEW_CHANGED` if it changed a mark, in which case the page reads the preview again and the user confirms what is really there. What is set aside is never decided by groups other than the ones that were shown. After an edit it runs only when a name changed. The scope is the tracks of the batch: a run on the whole library compares the whole library, a run on a selection only the selection.
- `pipeline/batch-duplicates.ts` does the work on the items of the batch (`groupBatchDuplicates`). The names are the ones the batch proposes, else the track's, else what the file name says, cleaned with `cleanNames` whether or not the batch ran the naming; the AcoustID is the one this batch's lookup found, else the track's. Each copy gets the entry `duplicate` in the `after` of its item (`group`: the lowest track id of the group, `keep`, `keeper`: the track of the copy that stays, `chosen`) and the `DUPLICATE` warning. A track a stage failed for is in no group. Grouping again keeps the copy the user picked as long as its group holds exactly one such copy. No table and no column was added.
- The apply stage `setAside` (`io`, not selectable, waits for `duplicates`) moves a copy that is not kept to `_Duplicates/<its name>` at the top of the folder the work happens in, through `TrackFiles.setAside`: the library in place, the clean library otherwise (the original then stays where it is, like every original). The move is backed up, journalled and undone like a rename, takes ` (2)` when the name is taken (reported as `NAME_COLLISION`), and never deletes. A copy the user took out of the batch is not moved, and neither is one whose kept copy is not in the library any more: `setAside` looks on the disk, under the track's lock, for the file of the track that stays, and fails the track when it is not a file or is itself set aside. The keeper is asked about a second time under the lock of the names, so its own rename in that moment is not taken for its absence. What stands at `_Duplicates` must be a folder or nothing (a link, a dangling link and a file are refused), and this is checked before the file is asked for, as is whether the file can be named there at all (a name the rule for new names refuses, no name left), so a refused set-aside makes no backup and does not become the batch that undo undoes. Among what was set aside (`freeNameFor`), a name that another track still has, though its file was deleted there by hand, counts as taken, for the move and for the rename that follows it.
- A folder named `_Duplicates` (`shared/duplicates.ts`, any letter case, any depth) is no part of the library: the scan does not enter it; it asks about each track that was set aside under the library by its own path instead. Only "not there" (`ENOENT`, `ENOTDIR`) counts as gone: the track is then marked missing, and, when the very same file (same size and modification time, which a move keeps) stands where it was before (`originalPath`), the track is pointed at it again and is in the library once more. Another file at that place is a new track. A track set aside in the clean library is outside the scanned folder and has no such way back by hand; undo is its way back. `listTracks`, `countTracks` and `listTrackAvailability` leave its tracks out, and a run refuses them. A library root or a clean library folder that is, or is inside, a `_Duplicates` folder is refused. The row of a track that was set aside stays, for undo; "set aside" is read from the path, not stored. The style folders and the Rekordbox XML (T-022, T-032) must leave these tracks out through the same rule. The app deletes nothing from `_Duplicates` on its own; emptying it is the user's. Undo of the batch that set a copy aside takes that copy out of it again (see the open point about undo below).
- Two apply stages may now change the file of one track (`rename` and `setAside`), each with its own `TrackFiles`. `Stage.after` orders them: a stage waits for the stages it names when they are part of the batch, and does not bring them in. `rename` comes after `setAside`, so a copy that is not kept gets its new name in `_Duplicates` and does not take, in its old folder, the name the kept copy is about to get. As a second guard `working()` asks the database where the file is before it trusts the path it remembers. If `setAside` fails for a track, its `rename` does not run.
- The scan counts a file at the `originalPath` of a track as known, not new, only when the track now lives outside the library, as a copy in the clean library does. A track that was renamed or set aside where it is has left its old place, and a file that turns up there is another file (before this task such a file was never scanned).
- Undo writes the backup over a file only when nothing is lost by it (`taken()` in `planUndo`). A place that another track has, under any letter case or Unicode form, is taken. A file there that is not the track's own counts as free only when it holds what the backup holds, byte for byte (`FileOps.sameContent`, a streamed sha256, read only for these few files): that is an original put back already, by an undo that stopped half way or by the user. The same test applies when the track's row says it is at its old place although the batch moved its file away. Anything else stays, and the original is restored beside it as ` (2)`.
- The scan asks `BatchFiles.restoredOriginals` once (`knownFiles`): the places where a file of the last batch that wrote stands again as its backup holds it while its track still points elsewhere. Such a file is known, not a new track, so an undo that stopped half way can be run again after a scan and ends with the library as it was.
- The side of undo that deletes checks too, since T-016: see `isOwnFile` under tag writing.
- The Library page reads its list again when a batch was applied: names and membership may have changed while the page was open.

Online lookup (T-014):

- Two compute stages. `fingerprint` (`cpu`, not selectable) asks the sidecar's `fingerprint.compute` and keeps the answer in `lookup_cache` under the source `fingerprint`, for the file as the last scan saw it (track id, size, modification time). It does nothing while no AcoustID key is set. A file that cannot be fingerprinted does not fail its track: the lookup then goes by names. `lookup` (`network`, selectable, waits for `fingerprint`) runs the chain and proposes.
- In the sidecar, `fingerprint.py` decodes the first two minutes with the app's ffmpeg (as for tempo and key) and hands plain samples to `fpcalc` on its standard input. fpcalc never sees a library file: its own FFmpeg can open network addresses. The length of the whole track comes from the tag reader. The fingerprint is the one fpcalc makes of the file itself; a test compares the two.
- `services/lookup/`: `http.ts` (one request: the app's User-Agent, 6 s, at most 1 MiB, no redirect, JSON or a `LookupError`; a track asks up to four in a row inside the 30 s of its stage; a picture for a cover is the one exception, see Covers), `rate-limiter.ts`, one client per service, `confidence.ts`, `chain.ts`. The clients get their cache and their keys handed in; `pipeline/lookup-cache.ts` puts the cache on the `lookup_cache` table.
- Limits, counted by when a request starts: AcoustID 3 a second, MusicBrainz 1 a second, Discogs 60 a minute. A service that answers 429 or 503 is left alone for as long as its `Retry-After` says (at least 1 s; 60 s for a 429 that names no time), and the request is made once more. While a pause is longer than 5 s, requests to that service are refused at once instead of waiting, so a stage does not run into its 30 s limit: the track goes on without that source.
- The chain for one track (`lookupTrack`): AcoustID by fingerprint, then MusicBrainz for the recording of its best match (of several recordings, the one named most like the track); without a match that is sure enough to take, a MusicBrainz text search by the tags, or by the file name where a tag is missing, and the surer of the two candidates stays; then Discogs for the label, and for the year if MusicBrainz has none, or as a candidate where nothing else named the track. A source that cannot be asked, or has no key, is left out and the chain goes on.
- Confidence (`confidence.ts`): by fingerprint 0.6 × AcoustID score + 0.3 × text similarity + 0.1 × length match; by text 0.75 × text similarity + 0.25 × length match. Text similarity is normalized Levenshtein over artist and title without case, accents and punctuation; lengths match within 3 s.
- From 70% on, artist, title, album, year and label are proposed, each with the service it came from. Below that nothing is taken: the tags of the file are proposed as they are, with the source `id3`, and the stage reports `LOW_CONFIDENCE`. "Not found" is only said when every source was asked: a track without a match for which a service could not be asked fails with `LOOKUP_FAILED` instead, and the next run asks again (what did answer is kept).
- Every answer is kept, "no match" included, by source and query; a request that failed is not. A second run therefore sends nothing. The key of a kept AcoustID answer is the hash of the fingerprint. Only a refresh from the preview asks again.
- The AcoustID and MusicBrainz ids of a match are stored next to the fields (`identifiers`) and written to the track when the batch is approved, like tempo and key; an id that was not found never replaces one the track has. The names are not: they reach the track with the stage that writes the tags (T-016).
- Text from a service is cleaned before it is kept (`lookup/text.ts`): one composed line of at most 300 characters, without halves of characters, private-use and unassigned code points and letters that show as nothing.
- In the sidecar, ffmpeg and fpcalc run through `run_tool`, which looks every 0.2 s whether the job was told to stop and kills the tool then, so a stopped fingerprint job leaves no process behind.
- Differences from the plan: the text search also runs after a fingerprint match below 70% (the plan runs it only without a match; a wrong tag would otherwise keep a good fingerprint from ever being confirmed by name); the AcoustID key goes in the body of a POST, not in the address; MusicBrainz is asked with `inc=artist-credits+releases+release-groups` (`labels` is no include of a recording, so the label comes from Discogs); the limiter is the app's own, not `p-queue`. Beatport is not asked at all: its search page answers the app's User-Agent with a bot check, and the app does not pose as a browser. With it went the mix name and genre from Beatport and the cross-check of an online tempo and key.

Covers (T-019):

- The compute stage `cover` (`network`, selectable, after `lookup` when both run) looks at the cover a file holds with the sidecar's `cover.inspect` (Pillow reads its size; the front cover, else the first picture). A cover of 300 × 300 or more stays as it is, byte for byte, and costs no request. A track without one, with a smaller one, or with one that cannot be decoded gets a new one. A WAV gets none (its cover comes with its conversion, as its tags do), nor does a copy set aside into `_Duplicates`.
- Where it looks, in order (`services/lookup/cover.ts`, `findCover`): iTunes Search (`itunes.ts`, `entity=song`, five results) by the artist and title the batch holds, a song taken only when its artist and its title are each at least 80% alike (normalized Levenshtein, the title also with the mix in brackets), its `artworkUrl100` asked at `600x600bb`; then, only when iTunes has nothing that gives a cover, the lookup of the track (`lookupTrack`, from kept answers where there are any): the Cover Art Archive `front-1200` of the MusicBrainz release of a match of at least 70%, then the picture Discogs names for the release of the match (`cover_image` of the search answer, which needs no second request). The first candidate the sidecar can make a cover of wins. Beatport is not in the chain. After every service, the thumbnail a download left for a track that is still in the Inbox under the id yt-dlp named it by (`findThumbnail`, T-034) is made a cover, as a picture the user chose is (`importPicture`, `cover.prepare` with `manual`, so a WebP is taken), with the source `thumbnail`. A track with no cover of its own and none in the chain gets a placeholder (T-020).
- The MusicBrainz client keeps the id of the release it names as the album (`releaseId`), and the Discogs client the picture of each release (`image`, only an `https` address on `i.discogs.com`); `LookupResult` carries both for a match (`musicbrainzReleaseId`, `discogsImage`). Kept answers of the old shape fail their schema and are asked again once.
- A picture is downloaded by `LookupHttp.image`: no key, `Accept: image/jpeg, image/png`, at most 16 MiB, 15 s for the whole of it from the first request, an answer that does not say it is one of the two refused. The address comes from a service's answer, so it is fetched only from a fixed host per service over `https` on the default port (`isImageUrl`: `is<n>-ssl.mzstatic.com`, `coverartarchive.org` and `archive.org` with its servers, `i.discogs.com`). The archive answers a cover with redirects; they are followed by hand, at most three, each address checked before it is asked. iTunes Search and the archive have limiters of their own (20 a minute; 1 a second); the pictures have another, 10 a second per service, so a download does not wait behind the searches. A picture that is not there or that a server refuses sends the search on to the next place; only a service that cannot be reached or is busy counts as a failure. Tracks of one release that run together share one download of their picture.
- The covers folder (`services/covers.ts`, `userData/covers`, mode 0700, refused when it is a link) holds every picture by the SHA-1 of its address: `<sha1>.download` while the sidecar works on it, then `<sha1>.jpg` (the cover) and `<sha1>.thumb.jpg` (128 px, for the preview); the thumbnail of a file's own cover is named by the SHA-1 of the picture. A picture whose cover is there already is not downloaded again. The folder is kept between runs and never cleaned, by the owner's choice; about 100 KB a track.
- `cover.prepare(source)` in the sidecar (`fixlib_py/cover.py`) reads a download by its name in the folder the app named when it started the sidecar (`FIXLIB_COVERS_DIR`), decodes it only as JPEG or PNG after its size in pixels was read from the header (at most 16 million pixels; a JPEG is decoded at the smallest scale that still gives 600 px, a colour profile over 1 MB is not read), turns it upright by its EXIF orientation, into sRGB by its colour profile (one that cannot be read is ignored) and onto white where it is transparent, cuts it to a square around its middle when its sides differ by more than 2%, refuses it when that square is below 300 px, and resizes it to 600 × 600 with Lanczos. The cover is a baseline JPEG of quality 90 without EXIF or profile. Files are written into the folder as a temp file and renamed.
- The proposal: the field `cover` (the name of the cover, with the service as its source) and, next to it, `cover` with the thumbnail and what the file held (`coverDetailsSchema`). No cover found: the warning `NO_COVER`, and nothing changes. Not found while a service could not be asked: the track fails with `LOOKUP_FAILED`, as the lookup does, and the next run asks again.
- Embedding: the field is a tag field like the others, `cover` in `tags.write`, which takes only a name of the covers folder and reads that file as a 600 × 600 JPEG before it writes it, in place of every picture the file held (one `APIC`, type 3, `image/jpeg`). When the tags are written in the batch (`writeTags`), the cover goes in with them, in one write and one backup, and `embedCover` does nothing. Otherwise the apply stage `embedCover` (`io`, not selectable, waits for `cover`, after `convertFile`, `setAside` and `writeTags`, before `rename`) writes it alone, through `tags.would_change` and `replaceContent` as `writeTags` does. `commitApprovedValues` sets the track's `coverStatus` to `embedded`.
- The preview shows a "Borító" column for a batch that ran `cover` (`PreviewBatch.findsCovers`): the old thumbnail (marked as a deletion) and the new one, 24 px each. The page asks `preview:coverThumbs` for the rows it shows, at most 100 in one call, by batch and track id; main answers with `data:` addresses of the thumbnails (JPEG only, at most 256 KB), which the CSP allows. The source is named in the "Forrás" column ("iTunes", "Cover Art Archive", "Discogs").

Placeholder and manual cover (T-020):

- The end of the chain: when every place was asked and none gave a cover, a track that holds a cover of its own keeps it, however small, by the owner's choice (with `NO_COVER`, and the user can choose a picture), also a real picture the app does not decode (`cover.inspect` reports `other` for one larger than it decodes, whose size it reads from the header, and for a GIF, BMP, TIFF or WebP); a track with none, or with damaged bytes, gets one the `cover` stage has the sidecar draw (`fixlib_py/placeholder.py`, `cover.placeholder(artist, title, color)`): 600 × 600 on the colour of the track's style (the style the batch proposes, else the track's own, else Unsorted), the artist at the top and the title (with the mix, as the tag holds it) in the middle, each in Inter, as large as fits in two and three lines, cut with an ellipsis at the smallest size; the text white or nearly black, whichever has the greater WCAG contrast with the colour. The source is `placeholder` ("Generált"), and the row keeps the warning `NO_COVER`. A placeholder is named by the hash of what it shows, so the same text on the same colour is drawn once. Inter is in the repository (`python/fixlib_py/assets/fonts/`, SIL Open Font License, its SHA-256 checked by a test): `InterDisplay-SemiBold.ttf` of `Inter-4.1.zip` from github.com/rsms/inter/releases/tag/v4.1 (SHA-256 of the archive `9883fdd4a49d4fb66bd8177ba6625ef9a64aa45899767dde3d36aa425756b11e`); the build of the sidecar (T-041) must ship `assets/`. Widths are measured once per letter and scaled, and no more than 160 letters of a text are looked at, so the longest tag text is drawn in well under a second, also in letters Inter does not have (drawn as boxes). A placeholder that is refused or takes longer than its call may leaves the track without a cover, with `NO_COVER`. The JPEG of a placeholder carries the comment `FixLibrary placeholder`: `cover.inspect` reports it, so a later run looks for a real cover for such a track instead of keeping it as one of 600 px, and proposes nothing when it would draw the very placeholder the file holds (compared by the SHA-1 of the picture); an approved placeholder sets `coverStatus` to `placeholder`.
- What a placeholder shows is kept next to it (`cover.placeholder` of the item). The apply stage `redrawPlaceholder` (not selectable, waits for `cover`, before `writeTags` and `embedCover`) draws it again when the artist, the title or the style changed in the preview, and the batch holds the new picture in its place. The colour is that of the style the classification of the same run decided (T-021), else the style a track has, else Unsorted; a style changed outside the preview takes effect with the next run.
- A cover the user chooses: a double click or Enter on the "Borító" cell asks for a picture in a dialog of the main process (`preview:chooseCover`, which keeps the chosen path for that row, and `preview:setChosenCover`, which makes it the cover, so the page can say that it works on it), and a picture dropped on the cell is handed over by the preload, which alone can learn where the file is (`webUtils.getPathForFile`; `preview:dropCover`). Both end in `preview.setCover`, and the dialog opens only when `preview.canSetCover` says the row could take a picture: only for the batch that waits, ran `cover` and holds the row without a failure, a `.jpg`, `.jpeg`, `.png` or `.webp` file outside `/net/` and `/Network/` (judged as the path resolves, in any case; a share mounted under `/Volumes` is a drive the user mounted, and is accepted), read within 20 s, read once into the covers folder (`CoverStore.importPicture`: a regular file reached without a link, read into a buffer of 16 MiB and refused when it fills, named by the SHA-1 of its content); a picture that cannot be made a cover answers `COVER_UNUSABLE`, a row that cannot take one `INVALID_INPUT`. The field and what is kept next to it are written in one transaction, made a cover by `cover.prepare` with `manual` (which alone also decodes WebP), and proposed with the source `manual`; the warning `NO_COVER` goes. On approval the field `cover` is locked, so no later run looks for another cover for the track.
- The table of the preview knows a column whose cells start an action of the page instead of being edited (`activate`): the keys move to it like to a cell that is edited.

Tempo and key (T-013):

- `pipeline/stages/bpm-key.ts` is the compute stage `bpmKey`: `cpu` resource, 120 s, selectable. It asks the sidecar's `analysis.bpm_key` with the path of the track, a job id of its own for every attempt and the tempo range of the settings, and proposes the tempo rounded to a whole number and the key as its Camelot code, both with the source `analysis`. It reads the file and changes nothing.
- The answer is kept in `analyses` (type `bpm_key`) together with the range it was asked with, under the analyzer version (`BPM_KEY_ANALYZER_VERSION` in `shared/rpc.ts`, `ANALYZER_VERSION` in `analysis/bpm_key.py`; a test compares the two). A track is analysed again only when the version or the tempo range has changed, or when what was kept cannot be read. A file whose audio was replaced under the same name is not noticed.
- In the sidecar, `analysis/decode.py` turns the file into mono samples at 44.1 kHz with the app's ffmpeg (see the rules below), and `analysis/bpm_key.py` runs Essentia's `RhythmExtractor2013` (`multifeature`) and `KeyExtractor` (profile `edma`) on them in a worker of the process pool. Only the first 10 minutes of a file are analysed, which bounds what a job costs: measured on a file of that length, a worker peaks at about 260 MB while decoding and about 800 MB in Essentia, so a full pool of long tracks can take several GB. Audio shorter than 5 seconds has no tempo and fails the track.
- Octave correction: a measured tempo below the range is doubled and one above it is halved until it is inside (`fold_bpm`). The measured tempo is kept next to the corrected one.
- `shared/keys.ts` holds the 24 keys by pitch class, so two names of one pitch (`C#`, `Db`) are one key; `fixlib_py/keys.py` is its mirror. The main process maps the answer itself and refuses one whose Camelot code or name is not what its own table says.
- The preview's confidence of a tempo is Essentia's own (0 to 5.32), scaled so that what Essentia calls a weak guess (below 1.5) is below the 70% the preview flags. A key carries no confidence yet: how sure a key is cannot be told from Essentia's strength before it was compared with real tracks.
- Stopping: Essentia cannot be interrupted. A job that is told to stop answers at once and leaves its pool worker to finish the track, which takes seconds and only reads. After many jobs were stopped at once, the first jobs of the next run wait for those workers. There is no deadline inside a worker: a file that made Essentia hang would hold its worker until the sidecar ends.
- A worker that dies takes every job of its pool with it, and nothing says which file did it. The pool is replaced, and each of those jobs is tried once more in a pool of its own with one worker, so the file that kills its worker fails alone and the others get their result.
- The workers of every pool watch the sidecar and end when it is gone, however it ended (`new_worker_pool` in `server.py`); a worker would otherwise go on analysing a file after the app has quit.
- The stage keeps an answer only when its tempo lies in the range that was asked for.
- Not measured yet: the accuracy against Rekordbox on the real test set (`python/tests/test_bpm_key_real.py`, which runs only where `tests/fixtures/real/` holds tracks and their exported XML).

Python sidecar:

- One long-running process, started by `services/python-bridge.ts` when the app is ready and stopped on quit (`shutdown`, then SIGKILL after 3 s). It speaks JSON-RPC 2.0, one JSON document per line: requests on stdin, responses and `progress` notifications on stdout.
- The sidecar gets a fixed set of environment variables, not the app's environment, so secrets cannot reach it. `FIXLIB_FFMPEG` and `FIXLIB_FPCALC` among them name the tools of `services/binaries.ts`: the sidecar decodes and fingerprints with those and never with a tool on the `PATH`.
- The sidecar decodes a library file like this: it opens the file itself (no link in any part of the path, regular files only, `fixlib_py/files.py`) and gives it to ffmpeg as standard input, with `-nostdin`, `-protocol_whitelist pipe`, the input format forced by the file's extension, `-max_alloc` of 128 MiB, an empty environment and a timeout of 60 s. The allocation limit is what stops a file whose header claims an absurd sample rate: without it the resampler asks for gigabytes. ffmpeg opens nothing by name. Essentia's own loader is not used: the FFmpeg inside its wheel is old and has network protocols compiled in. The app's ffmpeg has no raw output format, so the samples come back as 16 bit WAV on a pipe.
- Every line from the sidecar is validated against `src/shared/rpc.ts`; anything else is logged and dropped. A line longer than 1 MiB counts as a crash.
- The sidecar keeps the real stdin and stdout for the protocol only: its own prints and its child processes get stderr and an empty stdin.
- When the sidecar dies, calls already sent are rejected with `PYTHON_CRASHED` and it restarts after 1 s, 2 s, then 4 s, at most 5 times in a row; 10 s of uptime ends the row. Calls made during a restart wait for the new process.
- In development the interpreter is `python/.venv/bin/python`. The packaged app does not start the sidecar until task 41 defines its runtime path.

Claude:

- `services/claude-cli.ts` is the only code that starts the `claude` command. It finds it with `zsh -lc 'command -v claude'` (an app started from the Finder has no shell `PATH`), then in the usual install folders; a path the shell names is used only if it is absolute, is named `claude` and is an executable file. Before every call the path is checked to be an executable file again. `check` reads `claude --version` and `claude auth status` (exit code 0 means logged in; of its output only the kind of subscription is read, never the email or the organisation).
- One call: `claude -p --output-format stream-json --verbose --json-schema <schema> --tools "" --strict-mcp-config --no-session-persistence --setting-sources "" --disable-slash-commands --system-prompt <text>`, the question on the standard input, in a new empty folder under `userData/claude-workdir` that is removed afterwards, with an environment of `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH` (the system's folders, then the folder of the command), `LANG` and `TMPDIR` only (no `ANTHROPIC_API_KEY`, so it runs on the login of the command). The folders a killed run left behind are removed at startup, and a link in the place of the working folder is refused. Not `--bare`. No model is named: the default of the subscription is used. The call may take 120 s.
- The stream is read line by line. The `system/init` message must be there and must list no MCP server and no tool but `StructuredOutput` (the tool the answer is given through); otherwise the call is stopped and its answer is not taken. The answer is the `structured_output` of the last `result` message. A call that ends without an answer after a `rate_limit_event` whose status is not allowed, an `api_retry` with `rate_limit`, or an error result with status 429 has run into the usage limit; a call that was held up and answered after all has answered. A process is given up two seconds after it was told to stop, and its output half a second after it ended, whoever still holds it open; `unknown option` on stderr with a non-zero exit means the installed command is too old.
- A question is a `ClaudeTask` (`services/claude-prompts/`): a system prompt, a prompt built from items with ids, the JSON Schema of the answer and a Zod schema for one entry of it. `style.ts`, `mood.ts` and `online-recs.ts` exist; the task for playlist prompts comes with its feature.
- `pipeline/claude.ts` gathers the items of one task into calls of at most 20 (`ask`), one call at a time. The ids are the places in the call: Claude never sees a track id. An entry that is not valid for an id that was asked about is asked for once more, with what was wrong in the app's own words (never quoting Claude); what the first try answered validly stays, entries for other ids are ignored, and items that are still invalid fail with `CLAUDE_FAILED`. Every call, also the test from Settings, takes its turn in one line; a call nobody waits for any more is stopped, and so is the running one when the app quits (`stop`). After the limit was reached no call is made for 15 minutes, also not the ones that were lined up before. An id that is missing from the answer is asked again once with the next call.
- The usage limit is not a failure of a track: `ask` rejects with `CLAUDE_LIMIT`, the orchestrator puts the job back in line, holds the `claude` resource of the queue (`pauseResource`), and lets it go again after 15 minutes; if there is still no room, it waits again. The other stages of the run go on, and `RunProgress.claudeRetryAt` tells the page.
- The command the user chose by hand in Settings is stored under the settings key `claude` (accepted when it answers `--version` as Claude Code does, whatever its file is called); without one, the command the shell finds is used. The status (version, login, what is wrong) is cached and asked again at most every five seconds. `system:testClaude` makes one real call about up to five tracks of the library and keeps nothing of the answer.
- The style decision (T-021) is the first stage that asks Claude.

Rekordbox XML (T-025):

- `services/rekordbox-xml.ts` serializes the collection (`writeRekordboxXml`): `DJ_PLAYLISTS Version="1.0.0"`, `PRODUCT`, a `TRACK` per track (`TrackID` the track's id, `Name` the title with its mix as the tag holds it, `Artist`, `Album`, `Genre`, `Kind`, `Size`, `TotalTime` in whole seconds, `Year`, `AverageBpm`, `BitRate`, `SampleRate`, `Comments`, `Label`, `Mix`, `Tonality` in musical notation, `Location`), hot cues as `POSITION_MARK Type="0"` (`Num` 0 = A … 7 = H, `Red`/`Green`/`Blue` from the Settings color of the slot), and under `ROOT` one playlist per style (`Type="1" KeyType="0"`, tracks by `TrackID`) and the folder `Playlists` with the user's playlists. A value that is not known leaves its attribute out; characters XML 1.0 cannot hold are dropped. A playlist whose name a sibling has, letter case aside, gets ` (2)`, ` (3)`; the folder `Playlists` keeps its name and a style of that name gives way. `Location` is `file://localhost` and the path as Node's `pathToFileURL` spells it.
- `pipeline/rekordbox-export.ts` (`exportRekordboxXml`) builds it from the database: every track of the library (`listLibraryTracks`; set-aside copies are no part of it), less the ones on a drive that is not connected and the missing ones; the genre is the primary style (else the tag's genre), the comment the rule the tag gets (`styleComment`). It refuses while files are changed or scanned (`RUN_ACTIVE`). Each track carries back Rekordbox's own grid as `TEMPO` markers (`Inizio` to the millisecond, `Bpm` to two places, `Metro`, `Battito`) from its `rb_grid`, so an import does not move it; a track without one has none. Cues and playlists are read from their tables, which T-029, T-037 and T-039 fill.
- The file is `fixlibrary.xml` in the generated-XML folder of Settings (default `~/Documents/FixLibrary`, made when missing; a folder the user chose must be there, so a drive that is gone is never stood in for by a folder on the startup disk). It is written whole or not at all: a new temp file next to it (`O_EXCL`), flushed, renamed over the old one. It is overwritten on every write. Right before the rename the export asks again whether files are being changed or scanned, and then keeps the old XML (`RUN_ACTIVE`). The temp files a stop left in that folder (exactly that name pattern, plain files) are removed before each write. A write may start at most every two seconds (`XML_BUSY`). An XML folder inside the app's data folder or the backup folder is refused.
- Settings warns (`xmlFolderWarning`) when that folder is on an external drive (`/Volumes`) or synced (iCloud Drive, `~/Library/CloudStorage`, `~/Dropbox`, and Desktop and Documents when iCloud keeps them, which is known by `~/Library/Mobile Documents/com~apple~CloudDocs/Documents` being there). The "XML írása" button of the Rekordbox card writes it (`rekordbox:writeXml`); the wizard of T-027 is to call the same.

Reading the Rekordbox export (T-026):

- `services/rekordbox-xml-read.ts` reads an export. The file is the newest `.xml` in the exported-XML folder of Settings, not `fixlibrary.xml`, no hidden file and no link (`findNewestExport`); it is opened once without following a link or waiting on a pipe, checked as it is open, and never more than 64 MB is read (`readExportBytes`). It is parsed in a worker thread (`rekordbox-xml-worker.ts`, built by electron-vite as its own chunk, `?modulePath`) with a heap of 1 GB and a minute at most, so a parse that runs out of either ends the worker, not the app (`parseExportInWorker`).
- `parseRekordboxXml` (fast-xml-parser's `XMLParser`) reads each `TRACK` (`TrackID`, `Location`, `AverageBpm`, `Tonality`, `TotalTime`, its `TEMPO` markers and `POSITION_MARK`s) and the playlist tree. The export is untrusted: refused with a DOCTYPE or entity declaration, every value validated; a track that does not fit is left out and counted (`skipped`), a marker or cue that does not fit is left out of its track, an empty number is no number. `Location` is read as Rekordbox writes it (`pathOfLocation`): `file://localhost/` or `file:///`, its escapes decoded but a `#`, `?` or lone `%` kept as part of the name, `..` and NUL refused, composed to NFC. Of two entries at one path the one with a grid is kept.
- `pipeline/rekordbox-import.ts` (`readRekordboxExport`) pairs the export with the library's tracks (those the app's XML holds) by path. The `TEMPO` list of each pair is stored as the analysis `rb_grid` (`{ tempos, exportedAt, readAt }`, `analyzerVersion` `rekordbox-xml`, read back with the import's bounds; migration 0007 adds the type); a paired track without a grid loses its old one, a track the export lacks keeps it (T-029 is to compare `exportedAt` with the file). It returns the check the wizard of T-027 shows: the library's tracks the export lacks, the export's entries whose file is not there (missing: only "no such file" counts), and the paired tracks without a grid; an entry on a drive that is not connected is counted as unavailable and not looked at, one in a network folder (`/net`, `/Network`, `shared/network-paths.ts`) or one the disk gave no answer for as unchecked. Each list goes to the page as its count and its first 200 entries, every path and name made one line (`toOneLine`). Refused while files are changed or scanned.
- The "Export beolvasása" button of the Rekordbox card reads it (`rekordbox:readExport`); writing and reading share one guard, one call at a time and at most one every two seconds (`XML_BUSY`). A missing export is `XML_NOT_FOUND`, one that cannot be read `XML_UNREADABLE`.

The Rekordbox wizard (T-027):

- The page `RekordboxWizard.tsx` leads the user through the steps they do in Rekordbox: the one-time setup (the "rekordbox xml" view, "Imported Library"), then phase A (write the XML, refresh, "Import To Collection", "Import Playlist", the analysis, removing the missing entries, "Reload Tag", the export, the check), then phase B (write the XML, refresh, import, export, and the cue check of `rekordbox:wizardCueCheck`). The texts are in `pages/rekordbox-wizard-steps.ts`, the steps and the state in `shared/rekordbox-wizard.ts`.
- Where the user is (`{ setupDone, step, enteredAt, exportFrom }`) is kept as the `rekordboxWizard` row of the settings table, so a wizard left halfway goes on after a restart (`pipeline/rekordbox-wizard.ts`); a row that cannot be read starts the wizard again. A step is done only when it is the current one; the XML step only once the XML was written since the step was reached; going back is to a step that was reached (the setup only while it is not done); phase A starts again only after the setup; phase B is refused while locked. The check (`checkWizardExport`) reads the newest export (T-026), judges it (`pipeline/rekordbox-check.ts`, `judgeExportCheck`: tracks not in it → import again, no grid → wait for the analysis, missing entries → remove them again; entries on a drive that is not connected, not looked at or not read keep it from passing too) and ends phase A only when it is clean; an export older than the moment the export step was reached (two seconds allowed for a coarse clock) does not pass. The check saves nothing when the wizard was moved while the export was read, and no step can be moved while an XML is read or written. `compareCues` (±10 ms) is the check of phase B, ready for T-029.
- Channels: `rekordbox:wizardView`, `rekordbox:wizardAction` (validated by `wizardActionSchema`, refused with `XML_BUSY` while an XML is read or written), `rekordbox:wizardCheck` (under the XML guard), `rekordbox:copyPath` (`xml` or `exportFolder`: the page names which, the main process resolves the path and puts it on the clipboard through `services/clipboard.ts`, once a second at most).

Stems (T-028):

- `fixlib_py/analysis/stems.py` (`analysis.stems`) separates a track with Demucs `htdemucs` into drums, bass, other and vocals and keeps, instead of the audio, the RMS of each stem in 100 ms windows as float16 in `userData/stems/<track id>.npz` (`FIXLIB_STEMS_DIR`, mode 0700; about 50 KB for ten minutes). The file is decoded with the app's ffmpeg as 16 bit stereo, at most 20 minutes (a longer track is separated for its first 20, and the answer says so: `durationSeconds`, `truncated`), kept as 16 bit, and separated a minute at a time with five seconds of context on each side, each minute made float on its own, so memory and the time of one step do not grow with the track. A job told to stop answers at once (also while ffmpeg decodes), and the worker ends after the minute it is in and writes nothing. The envelopes are written to a new temp file in the stems folder, opened by its descriptor, and renamed there; MPS gives back its cache after every track.
- The model is never downloaded by the app. `scripts/fetch-demucs-weights.sh` downloads the official htdemucs file once (pinned SHA-256, checked again by the converter) and `convert-demucs-weights.py` turns it into `resources/models/htdemucs/state.pt` (tensors only); the sidecar builds `HTDemucs` from arguments fixed in `stems.py`, loads the tensors with `weights_only=True` and `strict`, and checks what it built, so no file can run code or ask for another model (`FIXLIB_MODELS_DIR`; the packaged app gets the folder with T-041). It is loaded once in the single Demucs worker, on MPS with `PYTORCH_ENABLE_MPS_FALLBACK=1`, else the CPU; `TORCH_HOME` is `userData/torch`.
- The compute stage `stems` ("Stem-elemzés", selectable, `gpu`, 15 minutes per track, `STAGE_TIMEOUTS_MS.demucs`) keeps the answer as the analysis `stems` with the file's size and modification time; a track whose file did not change and whose envelopes are there is not separated again, so a run that was stopped or a restart goes on with the next track. It proposes nothing for the preview. Without the model every track fails with `PYTHON_ERROR`, and the log says once how to install it. The first time a run writes envelopes, `StemsStore.ensure` removes the temp files a stopped sidecar left and the envelopes of tracks that are gone.
- Measured in the spike of T-002: about 8 times real time on this M1 (a 6 minute track in about 45 s), so the whole library takes some 37 to 80 hours in the background, more than the half to one day of §07.

Hot cues (T-029):

- `fixlib_py/analysis/structure.py` (`analysis.structure`, mirrored in `shared/rpc.ts`, `STRUCTURE_ANALYZER_VERSION` `structure-house-1`) takes a track's id, Rekordbox's grid (its `TEMPO` markers, checked: 1 to 4000, time, tempo, `Battito` 1 to 16, `Metro`) and the duration, and reads the stem envelopes of T-028 by the id from the stems folder. It builds the beats of the grid (each marker's tempo up to the next marker), the bars from the downbeats counted on from `Battito`, and phrases of 8 bars from the first bar; the energy of each stem per beat is the mean of its envelope over the beat, per bar and phrase the mean over its beats; the pulse is drums + bass. The rules and their thresholds (`structure_params.py`, made for house) place A Start, B Bassline, C Vocal (empty for an instrumental track), D/F/H Drops, E Breakdown and G Outro, each at a beat of the grid: B and C go to a phrase start within 2 bars, else stay on their bar. A slot that breaks A < B, A ≤ C, Drop 1 < Breakdown < Drop 2, Outro after the last drop is emptied and the answer says `review`.
- The compute stage `cues` ("Hot cue-k felismerése", selectable, `cpu`, after `stems`, `STAGE_TIMEOUTS_MS.cues`) asks for them only for a track with an `rb_grid`; without one it proposes nothing and warns `NO_GRID` (the app never makes a grid of its own). It proposes the field `cues` (the letters, `A B – D E F G –`, against the cues the track had) and keeps the slots in ms as `cues` of the item; an emptied slot warns `CUE_REVIEW`. When the structure finds no cue at all, it proposes nothing and warns `NO_CUES`, so the track keeps the cues it has.
- The cues are the track's only when the batch is approved (`commitApprovedValues` → `pipeline/cues.ts` `writeTrackCues` → `db/cues.ts` `replaceTrackCues`, in the approval's transaction): every slot is named and colored as the Settings say, a slot the proposal leaves out is emptied, existing cues (also Rekordbox's) are overwritten, but a slot locked in `locked_fields` as `cue:<slot>` (set by the editor of T-030) and a track locked as `cues` are not touched.
- Phase B of the wizard writes the XML with the cues and the grid, and its check (`checkWizardCues`) reads the newest export: every cue of the app in its slot within ±10 ms (`compareCues`), and every grid the same as the one read before (`sameGrid`: 1.5 ms, 0.006 BPM, the same `Battito`). A clean check ends the wizard.
- `npm run eval:cues` (`scripts/eval-cues.ts`, `shared/cue-eval.ts`) compares the approved cues of the database with the owner's `tests/fixtures/real/cues.csv` (file name, slot, seconds) and prints the share within one bar and every miss in bars.

Cue editor (T-030):

- The page "Cue-k" (`pages/CueEditor.tsx`, `stores/cue-editor-store.ts`, `components/features/cue-editor/Waveform.tsx`) lists the tracks that have Rekordbox's grid (`rb_grid`), by the owner's choice; the filters are every track, "Átnézendő" (the latest batch that ran the `cues` stage to its end warned `CUE_REVIEW`, `listLatestProposalsOfStage`) and "Nincs cue". Enter or a double click on the "Cue-k" column of the preview opens a track in it.
- The waveform is `wavesurfer.js` 7 (pinned, added with the owner's approval), drawn from the peaks of `fixlib_py/analysis/peaks.py` (`analysis.peaks`: a hundred a second, per thousand of full scale, of the first 20 minutes), kept as `userData/peaks/<track id>.json` with the size and time of the file (`services/peaks-store.ts`, `FIXLIB_PEAKS_DIR`) and made again for a file that changed. A kept waveform is given at once; one is made at a time, and only for the track asked for last: asking for another stops the making of the one before (`job.cancel`). The beats, bars and phrases (eight bars from the first downbeat, as the structure counts them) are drawn over it from `shared/beat-grid.ts`; the cues are zero-length regions of the Regions plugin.
- The audio is played from the `fixlib-audio:` protocol (`services/audio-protocol.ts`, `fixlib-audio://track/<id>`): the main process takes a track id only, looks the file up (not offline, not missing, not set aside), opens it with no link anywhere in its path (`O_NOFOLLOW_ANY`) and without waiting on a file that is none (`O_NONBLOCK`), and serves byte ranges; at most eight responses hold a file open, the oldest is ended, and one not read for 30 s lets its file go. Chromium plays no AIFF, so an AIFF is served as a WAV of the same samples made on the way (`services/audio-stream.ts`: a header of 44 bytes and the samples with their bytes turned round, 16 and 24 bit), with no copy on disk. The CSP allows `media-src fixlib-audio:` and nothing else of it (no `connect-src`), by the owner's choice; T-033 plays through the same media element.
- Every edit is saved at once (`pipeline/cue-editor.ts`, `applyCueEdit`, the `cue-editor:*` channels): the page says where a cue was let go and whether Shift was held, and the main process snaps it to the nearest beat, or to the start of the nearest bar, itself, from the one track's grid. `shared/beat-grid.ts` and `beats_of` of the structure count the same beats, held to it by `tests/fixtures/grids/golden-grid.json`, which both test suites read. A placed or moved cue takes its name and color from the Settings; a deleted slot stays empty. Either locks the slot (`cue:<slot>`), so the next automatic run (`writeTrackCues`) leaves it as it is; "Vissza az automatikusra" releases the lock. "XML frissítése a Rekordboxhoz" takes the wizard to the first step of phase B (allowed once phase A is done).

A/B player (T-033):

- The preview of a batch that normalizes has an "A/B" column (64px, at every width): Enter or a double click on a row with a gain opens `features/preview/AbPlayer.tsx` in a dialog. One `<audio>` element plays the original file from `fixlib-audio:` into Web Audio (`createMediaElementSource`), through two gain nodes: A at 0 dB, B at the plan's gain (`shared/ab-player.ts`, `abGainsOf`; the gain of the plan is already in whole steps for mp3gain). A switch ramps both over 20 ms (`AB_CROSSFADE_S`); the place does not change, as one element plays both. Both ways of normalizing are a linear gain, so B is what the file will sound like; the small change of tone of a new 320 kbps encoding is not heard in it, as the plan accepts.
- An `AnalyserNode` after the branches gives the level shown ("Szint most", RMS of the last 0,74 s), by which the e2e test checks that B differs from A by the planned gain.

Loudness and normalization (T-031, T-032):

- `fixlib_py/analysis/loudness.py` (`analysis.loudness`, `LOUDNESS_ANALYZER_VERSION`) measures a file by EBU R128 with ffmpeg's `ebur128=peak=true:framelog=quiet`, the file as its standard input, and reads only the summary (`I:`, `LRA:`, the true `Peak:`). A file ffmpeg cannot decode, or a silent one (at or below −70 LUFS, or no finite peak), answers `unreadable`, which the stage turns into `FILE_UNREADABLE`.
- `fixlib_py/analysis/energy.py` (`analysis.energy_features`, `ENERGY_ANALYZER_VERSION`) decodes a file like `bpm_key` and runs in the shared CPU pool (`server.run_in_cpu_pool`, which both use: told to stop, it answers at once; a worker that dies is retried once in a pool of its own). It cuts the track into windows of 10 s, leaves out the silent ones (RMS at or below −60 dB), and keeps the 75th percentile over the rest of each feature: RMS (dB), percussive ratio (HPSS by median filters across time and frequency with scipy on the mono signal at 22 050 Hz, the percussive RMS over the whole), onset rate, spectral centroid and flux, and the share of 20–150 Hz. The integrated loudness is over all of it, gated by R128. Like `bpm_key`, only the first 10 minutes are decoded (`decode.MAX_SECONDS`), so a longer track is judged by those. The split is done in place, and a worker peaks at about 740 MB on a track of 10 minutes. Essentia's `OnsetRate` and `Flux` keep state and are reset for every window. The stage `energyFeatures` (selectable, `cpu`, 120 s) keeps the features as an `energy_features` analysis with the file's size and time, and analyses again only when the file or the version changed; it proposes nothing, the 1–10 value is T-024's. The tempo T-024 needs is the track's own from T-013.
- The energy calibration (T-024): `pipeline/energy.ts` keeps a sample of tracks to rate in the setting `energyCalibrationSample` (`selectCalibrationSample` in `shared/energy.ts`: 3 to 5 from every style of at least 10 measured tracks, spread over their scores, the small styles and the tracks without a style together in what room is left, 30 at most; before a model the score is the sum of the standardized features that rise with energy), the ratings in `energy_calibration`, and the model in the setting `energyModel`. `energy.fit` (`fixlib_py/analysis/energy_model.py`) is a ridge regression (λ 1) on standardized features with its leave-one-out mean error; it takes every rating of a measured track, of this sample and the ones before, and needs 10 that are not all the same; one fit runs at a time. Its leave-one-out error standardizes by the whole sample, a close and slightly kind approximation. "Új minta" chooses from the tracks not rated yet. The app applies its weights itself (`scoreOf`, a dot product). When it is fitted, the scores of every measured track set the scale of each style of at least 10 tracks and of the library (5th percentile is 1, 95th is 10), kept with the model: new tracks get a value on the scale of the last fit, and a new fit sets the scales again. A model of another `ENERGY_ANALYZER_VERSION` is not used. The stage `energy` (selectable, after `style`, needs `energyFeatures`) proposes the value on the scale of the style the batch gives the track, and nothing without a model or for a locked energy; `naming` follows it, so the file name carries it. `follows` (in `Stage`) orders two stages of a track like `after` but runs the later one whatever became of the earlier: a track whose style or energy fails still gets its name. A fit while a batch computes can give that batch values of two models; the preview shows what each row got. The commit writes an approved energy to `tracks.energy` unless the field is locked, like the tempo and the key: an undo puts the file back, the row keeps the value; the comment tag takes it through `organizeFile`. The page "Energy" (`pages/EnergyCalibration.tsx`, `energy:*` channels) shows the sample with a play button and a 1–10 choice per track, the count rated, and the mean error of the last fit.
- The similarity (T-036): `pipeline/similarity.ts` is pure. Two tracks score by style (the same primary 1, one's primary the other's secondary 0.6), tempo (1 within 3 BPM, falling in a line to 0 at 8), Camelot key (the same 1; one step with the same letter, 12 next to 1, or the same number with the other letter 0.8), energy (1 − |difference| / 9) and mood (the Jaccard similarity of the tags), weighed 0.35, 0.25, 0.20, 0.12 and 0.08; a value that is not known scores 0 in its part. `buildProfile` makes a playlist one profile: the share of each style pair, the median tempo, the set of keys, the mean energy and its three most frequent moods; a candidate scores against it by the style of every track weighed by its share, the median, the key that fits best, the mean and the moods. The stage `mood` (selectable, `claude`, follows `bpmKey`, `style` and `energy`) asks Claude (`claude-prompts/mood.ts`, twenty tracks a call) for up to three moods of a fixed list (`shared/mood.ts`, enforced by the JSON schema and read through its own schema) from the names, label, style, tempo and energy the batch has, and keeps them in `tracks.mood_tags` (migration 0008) as a cache, like an analysis: a track that has them is not asked again, and a batch that is cancelled or discarded leaves them, as an undo does. A track whose text, or style name, reads like it talks to the model (the words of the style task, and moods, choose, every track, all tracks) is asked about alone. It proposes nothing and writes no file. An Inbox batch leaves it out, with the stems and the cues, so the Claude limit never holds its preview up.
- Playlists (T-037): `pipeline/playlists.ts` creates, renames and deletes playlists and adds, removes and moves their tracks (`playlists:list`, `playlists:view`, `playlists:edit`, one `PlaylistAction` per edit), through `db/playlists.ts`: an add appends after the last place, a remove deletes one row, a move swaps the places of two (each in a transaction). A track is added at the end and once: one the playlist holds, one that is not in the library (gone, or set aside in `_Duplicates`, read for the ids asked only) or one beyond 5000 tracks is skipped and counted; there are 500 playlists at most. The view of a playlist gives its tracks, their length, tempo range and keys, and ten recommendations: every track of the library but those it holds and those offline or missing, scored by `profileSimilarity` against `buildProfile` of the playlist, the best first, the lower id first on a tie; none for an empty playlist. They are worked out again on every view, add and remove, about 30 ms for 5000 tracks; a move and a rename leave them as they were (`recommendations: null`). A track of the playlist set aside later shows as not available, and the XML leaves it out. The Rekordbox XML already writes these playlists, in their order, in the folder "Playlists" (T-025).
- Online recommendations (T-038): `pipeline/online-recs.ts`, asked for by a button (`playlists:onlineRequest`), one request at a time and 30 s apart (`ONLINE_RECS_BUSY` otherwise; each is a Claude call and up to 20 YouTube searches, and YouTube answers a burst with a bot check), kept in memory per playlist for the session (`playlists:onlineLast`, which also says whether that playlist is being asked for). Quitting stops a request and lets none start. Claude (`claude-prompts/online-recs.ts`, one item: the playlist) gets the profile (styles by share, median tempo, keys, mean energy, moods) and up to 20 tracks spread over the playlist, none whose text reads like it talks to the model, and names up to 20 candidates (artist, title, mix, a style of the user's list), read entry by entry. A candidate whose normalized artist and title a track of the library has is dropped before the search, so its names stay on the machine. Each other one is searched on YouTube (`yt-dlp -J --flat-playlist ytsearch1:<artist> - <title> <mix>`, four at a time) and kept when the hit lasts 2 to 15 minutes and its title, alone or after the uploader without " - Topic", is at least 80% alike (normalized Levenshtein) to the artist and title, with or without the mix (`verifiedHit`). A candidate the library has by the name rule of the duplicates (`findLibraryCopy`, with the video's length) is dropped. The rest are ranked by the style part of the profile score, tempo, key, energy and mood counting 0.5 each (`onlineScore`), Claude's order on a tie, and ten are shown. Beatport is no source (PRD §08): its genre Top 100 pages answer with a Cloudflare challenge (403), as its search does, so neither the Top 100 list nor the Beatport check exists, by the owner's choice. "Letöltés" (`playlists:onlineDownload`) takes only an address recommended for that playlist and asks about it through the downloads of T-034; a low bitrate or a copy in the library by the video's title is asked about in the row first ("Így is", "Mégis"), as the Letöltés page asks. It then starts the download and keeps `{videoId, playlistId, at}` in the setting `pendingPlaylistAdds` (200 at most; a download that has not become a track of the Inbox within 7 days is forgotten). When the Inbox watcher turns the file `Inbox/<videoId>.mp3` into a track, its id is noted; the next listing or view of playlists (`listPlaylistSummaries`, `playlistView`) adds every noted track that has left the Inbox, that is whose batch was approved, at the end of its playlist, and drops one that is gone or was set aside; without a library folder nothing is added.
- The playlist generator (T-039): `pipeline/generator.ts`, the page "Generátor" (`generator:*` channels). The curves are `shared/energy-curves.ts` (`energyAt`: warm-up 3→6, peak time 8, sunset 4→7 with two whole waves of ±1.5, closing 8→3, a drawn curve of 5 to 10 points joined by lines). The tracks it uses are those of the library with a tempo, a key and an energy, online and present, in the tempo range, and for a set in minutes with a length. A beam search keeps the five best partial lists; each is continued with its eight best next tracks (kept in one pass, not by sorting) that mix with the last one placed (`mixesWith`: the same key or a Camelot neighbour, `keyScore` > 0, and 3 BPM at most apart) and are not in it yet. The tracks that mix are found through an index made once per generation (`createMixIndex`): the tracks grouped by key and each group ordered by tempo, so only the mixing keys within 3 BPM are read. A place is scored 0.45 by style (the order of styles is split over the set by time, both styles taken within 5% of a change; a secondary style counts 0.6), 0.45 by how near the energy is to the curve (1 − |d| / 9), and 0.1 by mood; the lists are compared by their mean score. A place no track can take is a gap with the profile it should have had (the style of that time, the tempo and key of the track before, the energy of the curve), costs 1, takes the typical length of a track, and the next place is judged against the track before it. A set in tracks has places of equal time; a set in minutes ends at the first track that reaches its length. Measured on synthetic libraries: 46 ms for 200 tracks out of 20 000 of every key, 123 ms when all 20 000 share one key, 645 ms for 50 000 of one key and a ten-hour set of one-minute tracks (400 places, the cap); it runs in the main process. A prompt is read one at a time (`GENERATOR_BUSY`). "Csere" (`alternativesAt`) offers five tracks in the tempo range that mix with the nearest track on both sides (across a gap, as the generator judges it, the neighbours looked up among all analysed tracks) and are not in the list, judged by the parameters the list was generated with; the swap is the page's, the list lives in its store for the session only (the owner's choice). A prompt is read by Claude (`claude-prompts/playlist-prompt.ts`) into the fields it names: styles of the user's list in order (others are named back), minutes or tracks, the tempo range, a profile and moods; nothing is generated before the user presses "Generálás". "Mentés playlistként" makes a new playlist of the tracks (gaps left out) through `editPlaylist`. A gap asks for online recommendations by its button (`OnlineRecs.requestGap`, the target as the profile and no example tracks, by the same rules and 30 s spacing as a playlist's), and a download from there goes to the Inbox only.
- The compute stage `loudness` (`cpu`, not selectable, `STAGE_TIMEOUTS_MS.loudness`) keeps the measure as the `loudness` analysis with the file's size and time, and in `tracks.lufs` and `tracks.true_peak_dbtp`; a file that did not change is not measured again.
- The plan is pure TypeScript in `shared/normalize.ts` (`planNormalization`), not a `normalize.plan` RPC as the plan of the task says, so that the preview, the apply stage and the A/B player of T-033 compute one gain. Gain = target − measured. An MP3 in lossless mode gets `round(g / 1.5)` steps (half away from zero) for mp3gain, in exact mode the exact gain, encoded again; an AIFF or a WAV always the exact gain on its samples. A raise that takes the true peak above −1.0 dBTP is skipped with `CANNOT_NORMALIZE` and the needed and possible gain; a gain that lowers is always applied; a raise above 39 dB (26 steps) is skipped the same way; less than one step, or 0.1 dB, is "at target".
- The compute stage `normalize` ("Hangerő-normalizálás", selectable, after `loudness`) reads the target and method of the Settings, proposes the fields `lufs`, `truePeak` and `gain`, and keeps the plan as `normalize` of the item (`pipeline/normalize.ts`); the preview takes the measured values as the cells' before, and gives each row `normalization` (method, action, gains of a skip).
- `fixlib_py/normalize.py` (`normalize.apply`) writes into the temp file of the file rules: `mp3gain -T -g <n> -s s -q` on a copy (in the file itself, so no file of mp3gain's own appears in a library folder; the size must stay the same), the samples of an AIFF or WAV (16 or 24 bit PCM) multiplied in place with TPDF dither at 16 bit (not on digital silence) and every other byte kept, or ffmpeg `volume=<g>dB` with `libmp3lame` at 320 kbps and the source's ID3v2 tag, cover included, written back as v2.3. The mp3gain of the app reaches the sidecar as `FIXLIB_MP3GAIN`.
- The apply stage `normalizeFile` (`io`, not selectable, waits for `normalize`, after every other stage that changes the bytes of the file) first measures the file as it is (a step run again on a resume may find the gain in it already, and then does nothing), then runs `normalize.apply` through `replaceContent` on the content it hashed, and measures the written file again. It comes after every other step that changes the bytes, and before `rename` and `organizeFile`, which move the file. Off its plan (more than 0.2 LU exact, 0.75 LU by steps, or a raised peak above −1.0 dBTP, each with 0.05 or 0.1 dB for how near ffmpeg measures) the track fails with `OFF_TARGET`, by the owner's choice: the file stays as written and the batch can be undone. The measure after the apply is kept without the file's time and never reused, because the row keeps the time of the file before and mp3gain keeps its size; an undo puts back the row of before the batch, where the track was not measured yet.

Style folders and genre and comment tags (T-022):

- The compute stage `organize` (`cpu`, selectable as "Mappába rendezés", after `style`, listed after `duplicates`) proposes the folder a track goes into (`folder`) and its genre (`genre`), both with the source `organize`: `<root>/<primary style>/`, the style the classification of the same run decided, else the track's own, Unsorted where there is none (`stages/style-tags.ts`, `styleFolderOf`; the folder name made safe by `folderNameOf`). It keeps the names of the styles with its proposal, so the folder follows a style changed in the preview (`recompute` now gets the item with the fields as they are after the edit). A copy that was set aside, or that the batch sets aside, is not organized.
- Which new styles a batch creates is one rule for the preview, the tags, the folder and the commit (`pipeline/new-styles.ts`, `createsStyle`): of the first five its rows name, those the list has already or has room for, in the order of the batch; before the approval the rows left in, after it the approved ones. A track whose new style is not created shows, gets and goes into Unsorted. The stage's `regroup` (after the compute phase, after an edit of a name or the first style, a row taken out or a copy kept, and before the apply) works it out for the whole batch; the orchestrator now asks the stages to regroup in the order of the stage list, so the duplicates come first.
- The apply stage `organizeFile` (`io`, not selectable, waits for `organize`, after every other stage that changes the file, `rename` included) works the folder out again (never takes it as stored), writes the genre (TCON: the primary style) and the comment (COMM: `E<energy>` and the secondary style, those of them there are, joined by `|`; one comment without a description in place of every such comment the file held, by design; frames with a description, such as `iTunSMPB`, stay) unless `writeTags` of the batch carried them already, then moves the file into its folder with `TrackFiles.organize`: the root is the library in place, the clean library otherwise; a file right in its folder already is not touched and costs no backup; a taken name gets ` (2)`. The subfolders of the old structure are flattened.
- After the move, the folders the file left that hold nothing but Finder's `.DS_Store` are deleted, from its old folder upward (`FileOps.removeFolderOfFinderData`), never the root, a style folder (of the list, or one the batch creates, by the name its folder has) or a folder of the app's own; a folder that holds anything else stays. This tidying is best effort: it follows no link, checks that the folder is still the one it looked at before each removal, and never fails the move. `TrackFiles.organize` refuses the name of an app folder. Undo puts the files back through their backups, which makes their folders again, and removes the folders it leaves empty, a style folder also with only a `.DS_Store` in it; a folder of the app's own only when it is empty, as before.
- The genre the batch wrote is the track's (`tracks.genre`) once it is applied.
- The new paths reach Rekordbox only through the XML (T-025, T-027).

Style classification (T-021):

- The scan reads the genre of a file's tag (TCON, an ID3v1 number named; at most 100 UTF-16 units, counted alike on both sides) into `tracks.genre` (migration 0006). A track read by a scan before that is read once more for it (`stageStatus.genre`, dropped again when a file can no longer be read), whether or not its file changed. All tag text is cut in UTF-16 units, as the main process measures it. A scan reads 40 files a call, so that the answer of one call stays below the line limit of the bridge with the field added. The Discogs client keeps the genres and styles of each release (at most ten names of 60 characters), and `LookupResult` carries them for a match (`discogsGenres`, `discogsStyles`). Beatport is no source (PRD §08).
- A remix is looked up as the remix: when the mix ends in `Remix`, `Edit`, `Rework` or `Bootleg` (`shared/remix.ts`), the MusicBrainz text search and the Discogs search ask for the title with the mix in brackets first, and without it when that finds nothing; what the first search found is measured against the remix's title, so that its original cannot win. A match by fingerprint is as it was. Who made the remix is read from the mix name (`remixerOf`: `Bicep Remix` → `Bicep`; `Radio Edit` names no one).
- The compute stage `style` (`claude`, selectable, waits for `lookup`) asks Claude through `pipeline/claude.ts` (twenty tracks that run together are one call) with `claude-prompts/style.ts`: the house and the other styles of the list, and per track its artist, title, mix, remixer, label, year, tempo, the genre of its tag and the Discogs genres and styles of its release (from the lookup's kept answers). The answer per track is `{ id, primary, secondary | null, confidence 0–100, isNewStyle }`; a name is one line of at most 40 characters, and what it may be is the rules' to decide. A track whose text reads like instructions (`looksLikeInstructions`) is asked about in a call of its own. A track with no genre at all is not asked about. The stage reads the lookup's kept answers only (`keptOnly`): it sends no request of its own; what was not kept counts as a source that could not be asked.
- The app's rules decide (`pipeline/style.ts`, `decideStyle`): no genre, a confidence below 70, `Unsorted`, a name that is neither in the list nor said to be new, a new name with a house in it (`isHouseName`: "house" anywhere, or a word within one letter of it), a new name none of the track's own genres names, or one that is no plain genre name (`newStyleNameSchema`) make the track Unsorted, with the warning `UNSORTED`. Names are compared without case, spaces, hyphens and the like (`styleKey`), so `Tech-House` is `Tech House` and `Hip-Hop` is `Hip Hop`. The secondary style is one of the list other than the primary, or none. A style the user set by hand (locked) is not looked at.
- The proposal: `styleId` and `secondaryStyleId` with the source `claude` and the confidence; a new style is `styleId` null with its name kept next to it (`style.newPrimary`), shown as "Új stílus: <name>". The approval names the new styles it creates. On approval `commitApprovedValues` creates it (`addStyle`: not a house style, the last before Unsorted, or the style of that name if one came since; five at most per batch, the first its approved rows name (`newStylesTaken`, the rule the page counts by too); none once the list holds 50; a track whose style is not created is Unsorted) with the color the classification gave it (`newStyleColor`: of the colors of `NEW_STYLE_PALETTE`, the default cue colors, no style has, the one the name picks, so the placeholder of the run and the style agree), and writes both styles to the track where they are not locked. A style the user chose in the preview is locked, as before; a first style set to what the second one is takes the second one away, and the second style is never the first. The styles are the track's own in the database only; the genre and comment tags and the folders come with T-022.
- A placeholder drawn in the same run takes the color of the style the classification decided (the `cover` stage comes after `style`; a new style's color is the one it will get).
- `scripts/eval-styles.ts` (`npm run eval:styles`) compares the primary styles in the database with `tests/fixtures/real/styles.csv` (file name, style) and prints the match rate and the differences; it runs on Electron's Node, because the database module is built for it.

Downloads (T-034):

- The page "Letöltés" takes addresses (one a line) or a search of YouTube or SoundCloud (`yt-dlp -J --flat-playlist ytsearch10:<query>` or `scsearch10:`; ten hits, each named by its page). `pipeline/download.ts` asks yt-dlp what each address is first (`-J --no-playlist`, read by `readInfo` in `shared/download.ts`): an answer that names more than one track (a playlist, a set, a profile) is refused (`DOWNLOAD_PLAYLIST`); an address with `list=` gives the one video. The bitrate is that of the best audio-only format (`bestAudioKbps`); below 128 kbps the page asks before it downloads. The title is read as `Artist - Title (Mix)` (`parseFileName`, `cleanNames`; the uploader is the artist where the title names none) and compared with the library by the name rule of the duplicates (`findDuplicateGroups`, `findLibraryCopy`): the same names, lengths 2 s apart at most. A match is asked about too. Only an address that was asked about can be downloaded (`download:start`), and it is asked about again for another download.
- `services/downloader.ts` runs yt-dlp: `-f bestaudio/best -x --audio-format mp3 --audio-quality 320K --embed-metadata --parse-metadata "title:%(artist)s - %(title)s" --write-thumbnail --newline`, the finished MP3 into `<library root>/Inbox/<id>.mp3` (`-P home:`), what it writes on the way into `userData/download-tmp` (`-P temp:`), so the Inbox only ever gets a finished file, and the thumbnail into `userData/thumbnails` (`-P thumbnail:`), never into the library. The Inbox folder is made inside a library folder that is there; the library itself is never made. The thumbnail is not turned into a JPEG: the app's ffmpeg has no picture codecs, and the cover stage reads WebP. `--max-downloads` is not used: yt-dlp ends with 101 when it is reached.
- Two downloads run at once (`MAX_PARALLEL_DOWNLOADS`), the others wait in line in the main process; not on the orchestrator's `network` resource, since a download is no stage of a batch. At most two questions to yt-dlp (what an address is, a search) run at once, and one starts at most every 300 ms. The list holds 50 downloads, finished ones forgotten first, and lives as long as the app runs. Progress is read from the `[download] n%` lines; the page gets the list at most four times a second, the newest last (`download:changed`).
- A failure says only its kind (`DownloadFailure`): `extract` when yt-dlp could not read the service's page ("Unable to extract", a failed signature, "Sign in to confirm"), where the page suggests a newer yt-dlp (task 43), `timeout` after 20 minutes, `missing` without yt-dlp or ffmpeg, else `failed`. What yt-dlp printed goes nowhere, not even to the log. Quitting stops the downloads and questions that run and fails what waits in line, so no yt-dlp outlives the app.
- Known limit: without a JavaScript runtime yt-dlp warns that YouTube may hide some formats; the best audio was there in every try.

Inbox (T-035):

- `<library root>/Inbox` is part of the library: the scan reads its files like any other, and "in the Inbox" is read from a track's path (`isInInbox`), not stored. `pipeline/inbox.ts` watches it with `fs.watch` (no `chokidar`, by the owner's choice) and lists it again every minute, for what a watch can miss and for a folder that appears later; a watch that ends is made again. An audio file (`.mp3`, `.wav`, `.aif`, `.aiff`, not hidden) is taken 10 s after it last changed, and only when its size and time are the same as at the last change, so a file still being copied waits. A file is offered once while the app runs (by path, size and time).
- The files that settled become one batch when nothing else is going on: no run, no batch waiting for approval, no scan, no file change, startup over (asked again every 15 s). So an Inbox batch never gives up a batch of the user's. The library is scanned first, then the tracks of the files are run (`createInboxBatches`), each track once while the app runs: the name a batch gives a file in the Inbox before `organizeFile` moves it is no new track. The functions are every selectable one but `stems` (hours of Demucs would keep the preview away), `cues` (hot cues need Rekordbox's grid, which a new track gets from the wizard) and `mood` (a Claude call for every file); the energy is proposed once the model is calibrated.
- The preview knows an Inbox batch (`PreviewBatch.inbox`: every track of it was in the Inbox) and shows the folder as "Célmappa" at every width; the folder follows the style chosen in the preview, as for every batch that organizes. Approved, `organizeFile` moves each file into its style folder, so the Inbox is empty; in clean library mode the copy goes into the clean library and the original stays in the Inbox, as every original stays. Duplicates are looked for among the tracks of the batch only (T-017's rule); the check against the library is the one before the download (T-034).
- Not covered: a batch that is given up leaves its files in the Inbox, and they come again only after a restart; a library chosen in this session is watched from the next listing, within a minute.

Errors:

- A failing track never stops a batch: it is recorded as `TrackError { trackId, stage, code, message }` and listed on the "Hibák" tab. `pipeline/run-stage.ts` is the one place that turns a failure into a `TrackError`: it runs one stage for one track, never throws, and aborts the work when its time is up (`TIMEOUT`). The orchestrator (task 9) stores the error in `batch_items.error`; the preview (task 11) lists it.
- Every stage has a timeout from `src/shared/timeouts.ts`, the only place where the limits are set.
- The message of a `TrackError` is always fixed text of the app, chosen by the error's code (`TRACK_ERROR_MESSAGES`). The text of the error itself, what the sidecar reported and what a tool printed go to the log only, each cut down to one clean line. An error the app did not raise itself is recorded as `UNEXPECTED`.
- Work that is abandoned on a timeout is told to stop through an abort signal. Its late result is ignored, but what it still does is not undone, so work that writes a file must stop on abort and never rename a temp file into place afterwards.
- Everything in the main process logs through `services/logger.ts`, into `main.log` in the app's log folder (`~/Library/Logs/FixLibrary/`; Electron spells the folder `fixlibrary`, which is the same folder on a case-insensitive disk). The file rotates at 10 MB and five files are kept. The sidecar writes its own `python.log` there with the same limits, and the bridge copies the sidecar's stderr lines into `main.log` with a `[python]` prefix, so both sides can be read in order. That copy is limited to 200 lines in ten seconds (what is held back is counted in one line), so a tool's progress output cannot push the app's own history out of the log. Both files are readable by the user only. If the log folder cannot be used, the app logs to the console and starts anyway.
- An uncaught exception in the main process is logged, the user is told in a dialog, and the app restarts (or stops, if it has run for less than 30 seconds, so a crash at startup cannot loop). The app never runs on in an unknown state while it may be writing library files. An unhandled promise rejection is only logged.
- `services/logger.ts` and the pure helpers in `src/shared` may be imported from every layer of the main process, including `db/`. Only `logger.ts` imports `electron-log`, and only its `/node` entry: the main entry registers IPC handlers outside `ipc/handle.ts`. ESLint enforces this.
- The UI shows a plain Hungarian message, never a stack trace or raw tool output.

## 05 Boundaries

Dependencies flow one way: renderer -> (IPC) -> main/ipc -> main/pipeline -> main/services and main/db. `shared` is imported by all and imports nothing from them.

Allowed:

- Pages import components, stores and `@shared` types.
- `ipc/` imports `pipeline/`; `pipeline/` imports `services/` and `db/`.
- `preload/` imports `electron` and `@shared` only.

Never:

- The renderer imports from `src/main`, uses Node APIs, or receives `ipcRenderer` itself.
- `services/` or `db/` import from `pipeline/`, `ipc/` or the renderer.
- Anything but `services/python-bridge.ts` spawns or talks to the Python sidecar. The one other use of the interpreter is `services/binaries.ts`, which runs yt-dlp as a module in its own short-lived process.
- Anything but `services/file-ops.ts` renames, moves, overwrites or deletes a library file.
- A command line built by string concatenation. External tools are spawned with an argument array, never through a shell.
- A secret in the renderer, in a log, or in plain text in the database.

## 06 Decisions that look wrong but are intentional

The agent must not "fix" these.

- Rekordbox is reached only through XML. `master.db` is never read or written, even though that would remove the manual import and export steps.
- Tags are written as ID3v2.3, not 2.4. Rekordbox and Pioneer players read 2.3 reliably.
- WAV files are converted to AIFF, and anything above 48 kHz is resampled to 48 kHz, so tags, covers and CDJ playback work.
- Normalization has no limiter. A track that cannot reach the target without exceeding −1.0 dBTP is skipped and flagged, not processed harder.
- Lossless MP3 gain runs `mp3gain` with `-s s` so no APEv2 tag is written.
- BPM and key come from our own analysis. Online values are only a cross-check.
- Claude is called through the `claude -p` CLI with tools and MCP disabled, from an empty working directory. No API SDK, and not `--bare` (it would bypass the subscription login).
- Demucs runs in its own single process, outside the CPU process pool, so the model loads once.
- Only the last batch can be undone; applying a new batch deletes the previous batch's backups.
- The preload is sandboxed and exposes hand-written functions. `@electron-toolkit/preload` was removed on purpose: it cannot be required in a sandbox.
- The renderer lives directly in `src/renderer/`, not electron-vite's default `src/renderer/src/`.
- React component and page files are PascalCase (`BatchPreviewTable.tsx`); everything else, including shadcn primitives, is kebab-case.
- `src/shared/keys.ts` and `rpc.ts` are mirrored by hand in Python (`keys.py`, method signatures). There is no code generation; both sides are kept in sync by hand in the same commit.
- The app is ad-hoc signed and not notarized. Do not add a signing or notarization step.
- Duplicates are detected and shown, never deleted automatically.

## 07 Scalability and future considerations

- Expected scale for v1: one user, one library of about 3000 tracks (25–35 GB) on an external drive, one machine (MacBook Pro M1). Build for this, not for 100x.
- Known limits: one Demucs job at a time, so the first full run takes half a day to a day (the T-002 spike projects 37 to 80 hours of Demucs time from synthetic input, see `python/SPIKE.md`; confirm on real tracks in T-028); one Claude call at a time in batches of 20; the Claude subscription limit can pause a run; exFAT drives make backups real copies; the full `.dmg` must stay under 2 GiB (GitHub Releases file limit).
- Planned next: nothing beyond the 45 tasks.
- Not planned: other platforms, other DJ software, multi-user, cloud sync, a plugin system. Do not add abstractions for these.

## 08 When the agent must stop and ask

If a task needs any of the following, stop, name the conflict, and propose the smallest change that avoids it:

- Crossing a boundary in section 05
- Changing a decision in section 06
- Adding a table, a dependency, a bundled binary, or an online service
- Changing how files are backed up, written, moved or deleted
- Changing how secrets are stored, or how the `claude` CLI is invoked
- Running anything against the real music library or `tests/fixtures/real/`
