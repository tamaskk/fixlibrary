- [ ] T-016 (F1, S) Tag writing (ID3v2.3). Before it, because it is the first stage that changes the bytes of a file (found by the reviews of T-015): a failed change must not leave its batch counted as one that wrote without need, which takes a rule that proves the file is unchanged (no journal row for the track, the same backup record, the same sha256 as the backup) and state kept per batch and track, not per stage; the rule against moving into a hidden folder must look at the folder as it is on disk, not as the path spells it. Done before it, in their own change: quitting waits for the file step that is under way before the database is closed; the tracks of an interrupted batch are told where their files are before every scan; `removeTempFiles` goes on after a file it cannot remove. Quitting also waits for an undo, without a limit, and for the pruning of backups. Still open from the review of that change, left for later with the owner's agreement because it deletes a file outside undo: on APFS a stop between the two halves of a rename (link, then unlink) leaves one file under two names, which nothing puts right; while quitting waits for an undo the window says nothing about it; an undo that a crash or a forced quit cuts between putting a file back and removing the renamed one leaves, when asked for again, a second copy named ` (2)`; after an uncaught error the database is still closed without waiting for file work; and for tag writing itself: its call to the sidecar must carry the job id and the abort signal, or a quit waits the full 30 s for it. Found with T-017: undo deletes the file under the name a batch gave it without checking what it holds; to tell the batch's own file from one put there since, `batch_files` needs the sha256 of what the batch wrote (a schema change, to be approved), which tag writing must fill in when it changes the bytes.
